LangGraph 图式智能体架构与生产实战精讲

深度拆解 LangChain 原生 Agent 到 LangGraph 状态机图的演进本质、确定性与自主性平衡、State Reducer 机制、线上 RAG 死循环全链路排查及高分求职动机表达。

Q1

LangChain 原生 Agent 与 LangGraph 实现的 Agent 的核心差异

架构演进 AgentExecutor vs StateGraph Pregel 消息传递
💡 核心速记：传统 LangChain 原生 Agent（基于 AgentExecutor）本质是封装死的“黑盒单向 while 循环”，主攻固定套路的单智能体 ReAct 调用；而 LangGraph 本质是受 Google Pregel 启发的“白盒有向循环图（Cyclic Graph）状态机运行时”，将节点（Nodes）、边（Edges）和共享状态（State）彻底解耦，原生支持细粒度循环控制、持久化断点恢复（Checkpointer）、人机协同（Human-in-the-loop）与多智能体协同。
🎙️ 面试 30 秒开口即答（逐字稿背诵版）

“面试官您好，这两者最本质的差异在于控制流抽象层级与状态管理方式。早期 LangChain 原生 Agent（如 AgentExecutor）是一个高阶黑盒封装，底层是硬编码的 while 循环：每一步完全依赖大模型判断是否调用工具，开发者很难在循环中途插入确定性的业务校验、强制路由或人工审批。而 LangGraph 是底层的有向循环图编排框架（StateGraph）：第一，在控制流上，它把推理、工具执行、业务校验拆成独立 Node，用确定性边（Normal Edge）和条件边（Conditional Edge / Command）显式控制流向，天然支持循环重试与分支回退；第二，在状态管理上，它维护强 Schema 约束的全局 State 和 Reducer 规约，而非简单的字符串或列表拼接；第三，在生产级工程能力上，LangGraph 原生在每个超步（Super-step）边界提供 Checkpointer 状态快照持久化，开箱支持断点续跑、人工介入（Interrupt）和时间旅行调试，因此现在 LangChain 官方也将新版的 create_agent 直接构建在 LangGraph 运行时之上。”

1. 全维度核心差异对比表

对比维度 LangChain 原生传统 Agent (AgentExecutor) LangGraph 实现的 Agent (StateGraph)
底层拓扑模型 黑盒伪循环（硬编码 while 循环）：固定执行 LLM Thought -> Action -> Observation 直到输出 Final Answer。 白盒有向有环图（Cyclic State Graph）：基于 Google Pregel 超步（Super-step）模型，支持任意分支、环路与并行节点。
控制流主导权 大模型全权主导 路由完全交由 LLM 决定，容易在复杂多步任务中迷失或偏离业务SOP。 混合编排可控 自由混合“确定性代码步骤”与“LLM 自主决策步骤”，关键节点可由代码强制路由。
上下文与状态管理 仅靠 intermediate_steps 列表追加与 Memory 包装器，难以精细控制多变量状态演进。 基于强类型 State（TypedDict / Pydantic）与独立通道 Reducer（如 add_messages、Overwrite）。
持久化与容错恢复 无原生断点能力 单次请求内存态运行，中途报错或超时需从头重跑，无法跨进程暂停。 原生 Checkpointer 每个超步结束自动保存状态快照，支持故障原地恢复与跨天长周期运行。
人机协同 (HITL) 极难实现，无法在工具执行前挂起线程等待前端用户审批后再继续。 原生支持 interrupt() 挂起与 Command(resume=...) 恢复，可在任意节点前审批或修改状态。
多智能体协同 只能将一个 Agent 包装成另一个 Agent 的 Tool，上下文隔离与交接（Handoff）笨重。 原生支持子图嵌套（Subgraphs）、多 Schema 私有通道与 Command(goto=..., graph=Command.PARENT) 跨图路由。

2. 执行拓扑与底层机制剖析

在传统 LangChain AgentExecutor 中，开发者只能传入 llm、tools 和 prompt，内部循环逻辑对业务代码封闭；而在 LangGraph 架构中，Agent 循环被显式拆解为可观测、可拦截的图结构：

【LangChain 传统 AgentExecutor（黑盒循环）】
User Input ──► [ AgentExecutor 内部黑盒: Prompt -> LLM -> Tool -> Observation ] ──► Final Output
               (痛点：中间步骤无法精确拦截、无中间快照、无法挂起等待人工确认)

【LangGraph StateGraph（白盒状态机图）】
START ──► [Node: Agent 推理] ──(Conditional Edge / Command 路由)──► END
               ▲                              │
               │ (State 更新经 Reducer 合并)     ▼
         [Node: 结果质量评估/重写] ◄── [Node: Tool 执行 / 人工 Interrupt]
         (每个 Super-step 边界均由 Checkpointer 自动持久化快照至 Redis/Postgres)

3. 生产环境选型准则（面试收尾升华）

  • 何时用高层封装（create_agent）：如果业务只是快速验证 PoC、或者属于单智能体标准的“查工具-回答”简单问答链路，直接使用高层预置封装即可快速上线。
  • 何时必须上 LangGraph（StateGraph）：只要业务涉及多步自我修正（如 Self-RAG / Corrective RAG）、敏感操作需人工确认（如退款/发邮件审批）、固定业务 SOP 与大模型推理混合编排，或者多 Agent 分工协作（Supervisor / Swarm 架构），必须直接使用 LangGraph 构建定制状态图。
🎯 面试加分项（展现对最新版本的认知）：在 LangChain 1.0 与 LangGraph 1.0 正式版架构中，传统的 AgentExecutor 已被全面标记为 Legacy（历史遗留组件）。如今哪怕调用 LangChain 高层的 create_agent，其底层运行时也已经是直接编译为 LangGraph 的 CompiledStateGraph——也就是说，“LangChain 负责模型与工具组件抽象，LangGraph 负责底层有状态编排运行时”。

Q2

LangGraph的图式架构，怎么实现“自主能力”与“稳定可控”的平衡的

架构设计哲学 确定性护栏 Human-in-the-Loop
💡 核心速记：LangGraph 实现平衡的核心哲学是“局部节点交给大模型自主推理，全局拓扑与状态边界交给代码确定性护栏”。具体通过五大抓手落地：① 混合节点编排（确定性代码 Node + LLM 推理 Node）、② 受限条件边与枚举路由（Conditional Edge / Command Literal）、③ 强 Schema 状态与幂等恢复（State + Checkpointer）、④ 人机中断（Interrupt）、⑤ 步数预算管控（RemainingSteps / recursion_limit）。
🎙️ 面试 30 秒开口即答（逐字稿背诵版）

“在企业级落地中，纯 Workflow 太死板，而纯 ReAct Agent 又容易脱轨。LangGraph 的图式架构通过‘把大模型的自主性关进确定性状态机的笼子里’来实现两者的平衡：首先，在节点层，它支持把处理复杂语义理解、工具选择的任务交给 LLM 节点发挥自主能力，同时把权限校验、参数清洗、兜底降级写成纯代码确定性节点；其次，在路由层，即便由 LLM 决定下一步方向，也必须通过 add_conditional_edges 或带有 Command[Literal[...]] 枚举约束的路由函数，确保只能跳转到白名单节点，绝不允许跳出预设图拓扑；最后，在运行保障层，配合 RemainingSteps 递归步数防御、Checkpointer 状态回滚以及高危动作前的 interrupt() 人工拦截，真正做到了‘推理有弹性、路径有边界、兜底有保障’。”

1. 为什么传统架构难以兼顾“自主”与“可控”？

  • 传统硬编码工作流（DAG / Pipeline）：100% 稳定可控，但面对用户模糊意图、多跳推理或工具报错自愈时毫无自主能力，分支稍微复杂就会沦为难以维护的 if-else 泥潭。
  • 纯自由 Agent（开放式 ReAct Loop）：虽然具备极强的自主规划能力，但把“流程控制权”完全让渡给概率性的 LLM，存在幻觉捏造参数、越权调接口、无限死循环等致命风险，无法满足生产级 SLA。

2. LangGraph 平衡“自主能力”与“稳定可控”的五大核心机制

机制维度 赋予的“自主能力” (Autonomy) 施加的“稳定可控”护栏 (Controllability)
1. 节点职责解耦
(Mix Nodes)		 在推理节点（Reasoning Node）内，LLM 可根据上下文自主决定调用哪个工具、生成何种查询词或自我反思（Self-Reflection）。 前置/后置节点直接使用确定性 Python/TS 代码实现（如规则校验、SQL 语法树检查、敏感词过滤），不依赖 LLM 概率输出。
2. 显式边与受限路由
(Edges & Command)		 通过 Conditional Edges 或 Command(goto=...)，允许根据 LLM 输出或工具结果动态分支、循环重试或并行扇出（Send）。 路由目标受编译期图拓扑与 Literal["node_a", "node_b"] 类型严格约束，只能走预设合法边，杜绝“野指针式”乱跳。
3. 状态契约与隔离
(State Schema)		 Agent 在多轮循环中可自主读写工作记忆（MessagesState、检索文档池、子任务计划）。 通过 InputState / OutputState / PrivateState 严格隔离读写边界，配合 Pydantic/TypedDict 与 Reducer 防止状态污染。
4. 人机回路中断
(Human-in-the-loop)		 常规只读查询与低风险动作由 Agent 全自动闭环执行，保障高效率。 涉及写库、资金、外部发送等高危动作时，触发 interrupt() 冻结当前状态快照，必须经人工审批或修正参数后才允许 resume。
5. 步数预算与降级
(RemainingSteps)		 允许 Agent 在遇到检索信息不足时主动发起多轮改写查询（Query Rewrite）与循环探索。 通过内置托管变量 RemainingSteps 及 recursion_limit 实时监控剩余步数，逼近阈值时由代码强行路由至优雅降级节点。

3. 代码级控制流实战范式（自主推理 + 确定性护栏）

from typing import Annotated, Literal, TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.managed import RemainingSteps
from langgraph.types import Command, interrupt

class AgentState(TypedDict):
    messages: Annotated[list, lambda x, y: x + y]
    retry_count: int
    is_high_risk: bool
    remaining_steps: RemainingSteps  # 托管步数计数器，保障稳定兜底

def agent_reasoning_node(state: AgentState):
    """【自主能力】由 LLM 自主分析意图并决定调用工具或生成回答"""
    # 若步数预算即将耗尽，主动收敛，防止失控
    if state["remaining_steps"] <= 2:
        return {"messages": ["已达最大探索步数上限，基于已有信息汇总回答..."]}
    # 正常调用 LLM 推理...
    return {"messages": ["LLM 自主推理结果"]}

def guardrail_router(state: AgentState) -> Literal["human_approval", "execute_tool", "fallback", END]:
    """【稳定可控】用纯确定性代码控制路由边界，不把流程控制完全交给 LLM"""
    if state["retry_count"] >= 3 or state["remaining_steps"] <= 2:
        return "fallback"            # 超过重试阈值，强制走确定性降级
    if state.get("is_high_risk"):
        return "human_approval"      # 高危操作强制进入人工审批节点
    return "execute_tool"

def human_approval_node(state: AgentState) -> Command[Literal["execute_tool", "fallback"]]:
    """【人机协同可控】挂起图执行，等待人工确认后再恢复"""
    decision = interrupt("检测到高危写操作，是否批准执行？(yes/no)")
    if decision == "yes":
        return Command(goto="execute_tool")
    return Command(update={"messages": ["人工拒绝执行该操作"]}, goto="fallback")
🎯 面试总结金句：“LangGraph 不是让大模型去写流程图，而是架构师先用图（Graph）画好跑道和护栏，再让大模型在跑道内自动驾驶——Node 内体现智能自主，Edge 上体现工程可控。”

Q3

LangGraph 的状态（State）机制，和传统 LangChain Chain 中沿链路传递上下文的方式，有什么本质区别

State & Reducer LCEL 管道 vs 状态黑板 Checkpointer 快照
💡 核心速记：传统 LangChain Chain（包括 LCEL a | b | c）是“函数式管道接力传参（局部变量流）”，上游输出即下游输入，无全局状态契约、无法天然支撑多轮循环覆写与断点恢复；而 LangGraph 的 State 是“带通道规约器（Reducer）与版本快照的全局共享状态机（Blackboard 模式）”，节点只返回局部增量更新（Partial Update），由底层引擎按各字段的 Reducer 原子合并，并在每个超步持久化快照。
🎙️ 面试 30 秒开口即答（逐字稿背诵版）

“这两者的本质区别可以概括为‘单向管道接力传参’与‘集中式状态机 + Reducer 增量归约’的区别。第一，在传统 Chain（如 LCEL 管道）中，上下文是点对点传递的临时字典，如果第 1 步生成的字段第 5 步要用，中间第 2、3、4 步必须用 RunnablePassthrough.assign 一路透传，一旦链路长或者有分支循环就会非常臃肿；而 LangGraph 采用集中式共享状态（Shared State Schema），所有节点读写同一个中心状态池，节点只需读取自己关心的字段并返回增量字典（Partial Update），无需手工透传无关字段。第二，LangGraph 引入了字段级 Reducer 合并机制：传统 Chain 赋同名 key 会直接暴力覆盖，而 LangGraph 每个状态通道可绑定独立 Reducer（例如用 add_messages 按消息 ID 智能追加或原地修订，用 operator.add 聚合并行分支结果，用 Overwrite 强制重置）。第三，LangGraph 的 State 与 Checkpointer 深度绑定，每一次状态演进都会生成可序列化、可回溯的版本快照，支持跨线程恢复与时间旅行，而传统 Chain 的上下文随着函数调用栈结束就销毁了。”

1. 本质差异全景对比：传统 Chain 上下文传递 vs LangGraph State 机制

核心维度 传统 LangChain Chain (LCEL / SequentialChain) LangGraph State 状态机制
设计模式范式 管道过滤器模式（Pipe & Filter）：数据像水流一样从 Step A -> Step B -> Step C 线性传递。 共享黑板 + 有限状态机模式（Blackboard / FSM）：中心化状态快照，各节点围绕同一 State 读写演进。
跨节点上下文传递 显式接力透传：中间节点即便不用某字段，也必须通过 RunnablePassthrough 携带，否则下游丢失。 按需读取 + 局部增量返回（Partial Update）：节点只返回修改了的 {"key": new_val}，未返回字段自动保留。
更新与并发冲突处理 简单字典覆盖（Dict Overwrite），并行分支同时修改同一列表极易互相覆盖丢失数据。 通道级 Reducer 二元归约函数：reducer(current_state, node_update)，安全合并并行超步写入。
多 Schema 视图权限 全局单一字典透传，内部临时变量容易泄漏到最终输出。 支持声明 InputState、OutputState 与内部私有 PrivateState，还要支持不落盘的 UntrackedValue。
生命周期与可回溯性 瞬态内存变量（Ephemeral）：仅存活于单次调用栈内存，进程崩溃或中途中断即彻底丢失。 持久化版本链（Checkpointed Snapshots）：每个 Super-step 生成独立 Checkpoint ID，支持断点续跑与状态回放。

2. LangGraph State 的核心灵魂：Schema + Reducer 归约器

根据 LangGraph Graph API 官方规范，State 绝不仅仅是一个 Python dict，它由结构契约（Schema）与通道更新法则（Reducers）共同组成：

  • 默认 Reducer（覆盖模式）：未声明 Annotated 时，新值直接替换旧值（适合保存最新路由标记、当前重写后的 Query）。
  • 累积型 Reducer（如 operator.add）：将左参数（当前累积状态）与右参数（节点增量返回）相加合并，天然适配 Map-Reduce 并行节点结果汇总。
  • 智能消息 Reducer（add_messages）：专为大模型对话历史设计。不仅支持追加新消息，还能追踪 Message ID——如果传入相同 ID 的消息（如人工修改某条历史消息或裁剪 Token），它会原地覆写该消息而非重复追加！
  • 强制重置原语（Overwrite）与非持久化通道（UntrackedValue）：当使用合并型 Reducer 需要清空错误缓冲区（如重试成功后清空 errors 列表）时，返回空列表 [] 会被合并而无法清空，LangGraph 专门提供 Overwrite([]) 绕过 Reducer 强制重置；而对数据库连接池、临时大缓存则提供 UntrackedValue，仅在运行时内存可见，不写入 Checkpoint。
from operator import add
from typing import Annotated, TypedDict
from langchain.messages import AnyMessage
from langgraph.graph.message import add_messages
from langgraph.types import Overwrite

class GraphState(TypedDict):
    # 1. 默认 Reducer：每次返回新字符串直接覆盖旧值
    rewritten_query: str
    # 2. 消息专用 Reducer：按消息 ID 智能追加或原地更新历史消息
    messages: Annotated[list[AnyMessage], add_messages]
    # 3. 列表累加 Reducer：多个检索节点并行执行时，自动将各自返回的文档列表合并
    retrieved_docs: Annotated[list[str], add]
    # 4. 错误日志累加通道：重试成功后可用 Overwrite([]) 强制清空
    errors: Annotated[list[str], add]

def clear_error_node(state: GraphState):
    # 仅返回需要修改的增量字段，未提及的 messages / retrieved_docs 毫发无损
    return {"errors": Overwrite([])}

3. Checkpointer 状态机快照与“时间旅行（Time Travel）”

传统 Chain 的上下文是一次性的“流水”，流过去就没了；而 LangGraph 的 State 在每个超步（Super-step）边界都会通过 Checkpointer（如 PostgresSaver / RedisSaver）按 thread_id 持久化。这带来了传统 Chain 根本无法实现的三大工程能力：

  1. 跨轮次长短期记忆统一：同一个 thread_id 下次请求时自动加载最新 State 快照，无需在外部手动拼接历史。
  2. 生产事故现场 100% 复现：线上某次回答出错，直接通过 graph.get_state_history(config) 拉取每一步的完整 State 演进轨迹。
  3. 状态分叉与时间旅行（Fork & Time Travel）：可以回到第 $N$ 步的历史 Checkpoint，用 graph.update_state() 修改当时的某个字段后重新向后执行，极大降低了复杂 Agent 的调试成本。
📚 权威参考源： LangGraph State & Reducers 官方文档 StateGraph Python API Reference
Q4

如果线上出现 Agent 反复调用同一个 RAG 工具、始终无法生成最终回答的死循环问题，基于 LangGraph 的能力，描述你的排查路径与定位方法

生产排障实战 GRAPH_RECURSION_LIMIT Corrective RAG 死循环治理
💡 核心速记：遵循“先止血观测 -> 再快照回放定位根因 -> 最后图架构级根治”三步法： ① 观测与还原：捕获 GraphRecursionError，通过 thread_id 调取 LangSmith Trace 与 Checkpointer get_state_history 检查每步的 langgraph_step、langgraph_triggers 及 ToolMessage； ② 定位四大高频根因：检索召回为空/低分导致评估节点无限打回重写、状态 Reducer 漏配导致 ToolMessage 未正确写回 messages、LLM 用完全相同的入参重复调工具、条件边路由缺少最大重试退出分支； ③ 架构根治：引入工具调用指纹去重、检索重写计数器 retry_count、内置 RemainingSteps 主动优雅降级与 recursion_limit 硬兜底。
🎙️ 面试 45 秒开口即答（逐字稿背诵版）

“遇到线上 Agent 反复调用同一 RAG 工具死循环并触发 GraphRecursionError，我会分排查定位和架构根治两步走。在排查定位上：第一，利用故障请求的 thread_id，通过 LangGraph 的 graph.get_state_history(config) 配合 LangSmith 追踪链路，调出每一个 Super-step 的状态快照（检查 config['metadata']['langgraph_step'] 和 langgraph_node）；第二，重点比对相邻两步的 State 差异，通常死循环逃不出 4 类根因——① 状态回写丢失（如工具返回的 ToolMessage 因自定义状态字段或 Reducer 配置不当没进入 LLM 上下文，导致 LLM 以为还没查过）；② 参数原地踏步（RAG 检索为空或相关度低，LLM 每次生成一模一样的 Query 反复查）；③ 评估阈值死锁（在 Self-RAG 中，grade_documents 节点判定相关性永远不达标，条件边无限打回 rewrite_query 节点，但没有设置最大重写次数）；④ 拓扑边混用（同一个节点同时绑了静态边 add_edge 和动态 Command，导致重复触发）。定位后，我会通过图级别检索计数器 + 工具入参 Hash 去重拦截 + RemainingSteps 主动降级节点彻底根治。”

1. 线上排查路径与精准定位四步法（基于 LangGraph 原生能力）

【线上 RAG Agent 死循环四步排查链路】
Step 1: 告警捕获 ──► 捕获 GraphRecursionError 或高延迟告警，提取请求 thread_id 与 run_id
                        │
Step 2: 状态时光机回放 ──► 调用 graph.get_state_history({"configurable": {"thread_id": tid}})
                        │  逐帧检查每个 Checkpoint 的 next (待执行节点)、values (State快照) 与 metadata
                        ▼
Step 3: 对比相邻 Super-step 的 3 个核心指标：
        ├─ ① 看 Tool Call 入参：每次 tool_calls[0]["args"]["query"] 是否完全相同？（同参死循环）
        ├─ ② 看 ToolMessage 回写：state["messages"] 中是否包含上一步的 ToolMessage？（状态丢失导致失忆）
        └─ ③ 看 Conditional Edge 判定：是 LLM 主动再调 Tool，还是相关性评估节点强行路由回检索节点？
                        │
Step 4: 时间旅行本地复现 ──► 取死循环发生前一步的 checkpoint_id，在测试环境 fork 状态单步调试修复

2. 死循环四大高频根因与定位特征矩阵

根因分类 Checkpointer 状态快照中的典型特征 底层原因剖析 针对性修复方案
根因 A：同参重复调用
(Identical Tool Call)		 连续多个 Step 中，AIMessage.tool_calls 的 name 和 args（查询词）100% 相同，ToolMessage 返回为空或无关文档。 知识库本来就没有该冷门问题的数据，但 System Prompt 强令“必须基于知识库回答”，LLM 不死心，拿原词反复查。 在 Tool 节点或前置拦截器中计算 hash(tool_name + args)，若已在 visited_queries 集合中，直接返回明确提示：“该查询词已执行过且无更多结果，请换词或直接告知用户暂无资料”。
根因 B：评估-重写死锁
(Grader-Rewriter Loop)		 节点轨迹呈 retrieve -> grade_docs -> rewrite_query -> retrieve 周期性交替，Query 虽有微调但始终过不了 grade_docs。 Corrective RAG / Self-RAG 架构中，条件边只写了 if relevant: generate else: rewrite，漏写了最大重试退出条件。 在 State 中显式维护 search_count: int，每次检索 +1；在条件边中判断 if state["search_count"] >= 3: return "fallback_generate"。
根因 C：状态回写失忆
(State / Reducer Bug)		 ToolNode 执行成功了，但下一轮进入 AgentNode 时，Prompt 里没有上一步的检索结果或 ToolMessage。 自定义 State 未正确使用 add_messages Reducer（或覆盖了列表），或者 Prompt 模板漏渲染了 ToolMessage / documents 通道。 修正 State Schema 为 Annotated[list[AnyMessage], add_messages]，并用 get_state_history 验证消息列表递增。
根因 D：动静态边冲突
(Edge Mixing Bug)		 单次超步中 langgraph_triggers 显示同一个检索节点被意外并发激活多次。 根据 LangGraph 官方规范，同一节点混用了静态 add_edge 和动态 Command(goto=...)，导致两条路径同时执行。 清理冗余静态边，同一节点的出边严格统一使用 add_conditional_edges 或 Command。

3. 基于 LangGraph 原生能力的三层防死循环根治代码

在生产环境中，不能只靠外部捕获 GraphRecursionError（Reactive 被动报错会直接中断用户体验），而应该结合查询去重 + 显式重试上限 + RemainingSteps 主动降级（Proactive 优雅收敛）：

from operator import add
from typing import Annotated, Literal, TypedDict
from langchain.messages import AnyMessage, SystemMessage, ToolMessage
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.managed import RemainingSteps

class RAGAgentState(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]
    rag_attempts: int                                # 第1层防护：显式记录 RAG 检索次数
    executed_queries: Annotated[list[str], add]      # 第2层防护：记录已检索过的 Query 指纹
    remaining_steps: RemainingSteps                  # 第3层防护：LangGraph 内置剩余步数托管变量

def rag_tool_node(state: RAGAgentState):
    last_ai_msg = state["messages"][-1]
    tool_call = last_ai_msg.tool_calls[0]
    query = tool_call["args"].get("query", "").strip()

    # 【防线 1：拦截同参重复调用】
    if query in state.get("executed_queries", []):
        warn_msg = f"【系统拦截】查询词 '{query}' 已检索过且无新增信息，请勿重复调用相同参数，请直接基于现有信息回答或告知用户未找到。"
        return {
            "messages": [ToolMessage(content=warn_msg, tool_call_id=tool_call["id"])],
            "rag_attempts": state.get("rag_attempts", 0) + 1
        }

    # 正常执行向量检索...
    docs = vector_store.similarity_search(query, k=3)
    content = "\n".join([d.page_content for d in docs]) if docs else "知识库未命中相关文档。"
    return {
        "messages": [ToolMessage(content=content, tool_call_id=tool_call["id"])],
        "executed_queries": [query],
        "rag_attempts": state.get("rag_attempts", 0) + 1
    }

def route_after_agent(state: RAGAgentState) -> Literal["rag_tool", "graceful_fallback", END]:
    last_msg = state["messages"][-1]
    if not getattr(last_msg, "tool_calls", None):
        return END
    # 【防线 2 & 3：超过 3 次检索 或 图剩余步数 <= 2 时，强制切断工具循环，走优雅降级汇总】
    if state.get("rag_attempts", 0) >= 3 or state["remaining_steps"] <= 2:
        return "graceful_fallback"
    return "rag_tool"

def graceful_fallback_node(state: RAGAgentState):
    """优雅降级节点：剥离工具绑定（不传 tools），强制 LLM 基于已有上下文给出最终答复"""
    prompt = state["messages"] + [
        SystemMessage(content="检索次数已达上限。请停止调用工具，立即基于已获取的上下文给出最合理的最终回答，缺失部分请坦诚说明。")
    ]
    final_response = llm_without_tools.invoke(prompt)
    return {"messages": [final_response]}
⚠️ 面试关键细节提醒：在调用 graph.invoke(inputs, config={"recursion_limit": 15}) 时，一定要向面试官指出：recursion_limit 是 config 字典的顶层独立 Key，绝不能塞进 config["configurable"] 里面（这是线上很多开发者设置了 recursion_limit 却不生效的常见踩坑点）。
