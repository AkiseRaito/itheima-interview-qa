Q1

结合业务说RAG流程，从离线知识库构建、在线检索召回、大模型生成三个阶段

RAG 全链路架构 Milvus 混合检索 + RRF Cross-Encoder 重排
💡 核心速记：结合企业级智能导购/客服业务（如《优车智选》259项质检标准与车型通病问答），生产级 RAG 分为三大闭环阶段： ① 离线知识库构建（ETL 解析清洗 ➔ 语义/父子切片 + 元数据注入 ➔ 双路向量化落库 Milvus/ES）； ② 在线检索召回（Query 意图路由与改写 ➔ 元数据过滤 + 稠密向量与 BM25 稀疏混合检索 ➔ RRF 初融 + Reranker 精排）； ③ 大模型增强生成（Lost-in-the-Middle 上下文组装 ➔ 强约束 Grounded Prompt 与护栏 ➔ SSE 流式生成与引用溯源）。
🎙️ 面试 45 秒开口即答（结合真实业务落地逐字稿）

“面试官您好，结合我主导过的《优车智选》智能导购与质检问答系统（承载了 259 项车辆检测手册、各品牌车型通病库及交易过户政策），我们的生产级 RAG 流程严格划分为三个阶段：第一是离线知识库构建阶段，核心解决‘脏数据与语义割裂’——我们用解析引擎提取 PDF/Markdown 中的文本和表格，按 Markdown 标题层级做结构化递归切分（子块 400 字用于精准检索，关联父块 1500 字用于还原上下文），并注入品牌、年款、文档生效时间等 Metadata，最后通过 text-embedding-v3 生成稠密向量与 BM25 稀疏词频同步写入 Milvus 集群；第二是在线检索召回阶段，核心解决‘搜不准与召回不全’——买家提问后，先做意图识别与多轮指代消解改写 Query，接着在 Milvus 中先按 Metadata（如品牌=宝马、状态=有效）预过滤，再并行发起 Dense 语义检索（Top-20）与 Sparse BM25 关键词检索（Top-20，精准命中发动机代号如 B48），经 RRF 倒数秩融合后，用 bge-reranker-large 交叉编码器精排截取高置信度 Top-5；第三是大模型生成阶段，核心解决‘幻觉与可信度’——我们将 Top-5 父块按首尾高权重重排注入 Prompt，强令模型仅依据参考块作答并输出角标引用（Citation），通过 SSE 流式返回前端，将回答准确率从纯向量检索的 72% 提升到了 91% 以上。”

1. 结合业务的 RAG 三阶段全链路工程细节表

阶段划分 核心工程环节 业务落地痛点（以智能导购/质检知识库为例） 生产级技术方案与关键参数
阶段一：
离线知识库构建
(Offline Indexing)		 1. 多源异构解析 (ETL)
2. 语义/父子切片
3. 元数据增强与向量化
4. 增量同步与版本控制		 PDF 质检报告含大量跨页表格；机械参数被定长切片截断后丢失主语（不知道是哪款车的油耗/故障）。 • 版面分析转 Markdown，表格转结构化键值对或独立摘要。
• 每个 Chunk 头部强行拼接文档路径前缀：[品牌:宝马 | 车系:3系 | 章节:发动机通病]。
• 基于文档 doc_id + content_hash 在 Milvus 向量库中实现幂等 Upsert 与过期文档软删除。
阶段二：
在线检索召回
(Online Retrieval)		 1. Query 理解与改写
2. Metadata 预过滤
3. 稠密+稀疏混合召回
4. Rerank 交叉精排		 用户口语化提问（“这车漏油严不严重？”指代不明）；纯向量检索对专有型号（如“EA888 Gen3”、“259项第14条”）不敏感。 • Query Rewrite：结合历史对话消解代词，复杂问题拆解为 Sub-queries。
• Hybrid Search：Milvus Dense HNSW + Sparse BM25 双路召回，通过 RRFRanker(k=60) 融合。
• Rerank：使用 Cross-Encoder（如 bge-reranker-v2-m3）对 Top-30 重打分并卡阈值（score > 0.65）取 Top-5。
阶段三：
大模型增强生成
(Augmented Generation)		 1. 上下文重排与压缩
2. 防幻觉 Prompt 组装
3. 引用溯源 (Citation)
4. 护栏校验与流式输出		 召回片段过多导致模型漏看中间关键条款；模型自由发挥编造售后保修政策，引发客诉风险。 • 上下文组织：将最高分片段置于上下文首尾两端，规避长上下文注意力衰减。
• 强约束生成：System Prompt 设定“拒答阈值”，无依据时触发兜底话术或转人工。
• 可观测评估：异步采集链路日志，使用 RAGAS / LangSmith 监控忠实度（Faithfulness）。

2. 生产级 RAG 三阶段架构流转与核心伪代码

【阶段一：离线知识库构建流水线 (Offline Pipeline)】
原始业务文档(PDF/Word/DB) ──► 版面解析与去噪(OCR/Table提取) ──► 父子层级切分(Parent:1500 / Child:400)
  ──► 注入业务Metadata(brand/year/doc_id/acl_role) ──► 双路编码(Dense Embedding + BM25 Sparse) ──► 写入 Milvus 2.5

【阶段二 & 三：在线检索召回与大模型生成 (Online Pipeline)】
用户提问 ──► 1. 多轮指代消解 & Query 改写 (LLM/小模型)
         ──► 2. 权限与业务标签过滤 (expr="status == 'active' and brand in ['BMW']")
         ──► 3. 双路并发检索: Dense Top-20 (语义相似) + Sparse BM25 Top-20 (型号/错误码精确匹配)
         ──► 4. 粗排融合: RRF (Reciprocal Rank Fusion) 合并去重得 Top-25
         ──► 5. 精排截断: Cross-Encoder Reranker 深度交互打分 ──► 过滤 score < 0.65 ──► 回表拉取 Top-5 父块
         ──► 6. 组装防幻觉 Prompt (附带 [Doc_ID] 引用约束) ──► LLM SSE 流式输出 + 护栏审计

3. 面试高频追问：怎么量化评估并迭代这三个阶段？（RAG 评估四象限）

  • 评估检索召回阶段（Retrieval Metrics）：重点看 Context Recall（上下文召回率）与 Context Precision / MRR@K（上下文精确率与平均倒数排名）。如果 Recall 低，优化切片粒度、引入 Query 改写或混合检索；如果 Precision 低，优化 Reranker 模型与过滤阈值。
  • 评估大模型生成阶段（Generation Metrics）：重点看 Faithfulness（忠实度/无幻觉率：生成的每句话是否都能在召回块中找到依据）与 Answer Relevance（答案相关性：是否正面回答了用户问题）。
🎯 面试加分项（展现企业级权限与增量更新细节）：在面试中主动提及“RBAC 权限过滤下推”与“知识库热更新幂等”会非常加分：千万不要等检索出 Top-K 后再在业务代码里做权限过滤（会导致过滤后只剩 0 条），而必须在离线构建时将 department_id / role_level 存入向量库 Scalar 字段，在检索时作为前置布尔过滤条件（Pre-filtering）下推给 Milvus 执行！

Q2

怎么解决上下文超过大模型限制的问题？

Context Engineering 多轮记忆裁剪与摘要 Lost in the Middle
💡 核心速记：解决上下文超限（及长上下文导致的高延迟、高 Token 成本与 Lost in the Middle 注意力退化）不能只靠换大窗口模型，必须按“四大工程维度”分层治理： ① 针对多轮对话历史超限：采用滑动窗口安全裁剪（trim_messages 保证 Tool Call 成对）+ 异步滚动摘要（Rolling Summary）+ 向量长期记忆（Store）； ② 针对 RAG 检索与 Tool 输出超限：采用Rerank 严卡阈值 + 上下文压缩（LLMLingua / Contextual Compression）+ 大文件卸载（Filesystem Offloading）； ③ 针对超长单文档分析超限：采用Map-Reduce 分块并行归纳或Refine 迭代精炼； ④ 针对模型底层架构：利用位置编码外推（RoPE / YaRN）、KV Cache 量化与 Prefix Caching。
🎙️ 面试 45 秒开口即答（逐字稿背诵版）

“面试官您好，在生产环境中，哪怕底座模型支持 128K 甚至 1M 窗口，当输入膨胀时也会出现严重的首字延迟（TTFT）飙升、Token 费用爆炸以及‘Lost in the Middle（中间信息迷失）’现象。因此我们在工程上会按上下文来源分三类解决：第一类是多轮对话历史超限，我们采用‘近期滑动窗口 + 远期滚动摘要’的混合架构——对最近 5 轮对话保留完整原文，对超出 Token 阈值的早期对话触发后台小模型压缩为一段精简的 ConversationSummary，并在裁剪时严格遵守消息边界（确保 SystemMessage 常驻，且 AIMessage(tool_calls) 与 ToolMessage 绝不拆散）；第二类是RAG 检索或工具返回内容超限，我们在检索端通过 Cross-Encoder 精排将召回块从 Top-20 压到高置信度 Top-5，并使用上下文提取器（Contextual Compression）剔除块内无关句子，如果工具返回了超大 JSON 或日志，则先卸载到沙箱文件或临时存储，只把摘要和分页游标返回给 LLM；第三类是超长单文档阅读任务（如百页合同审查），我们采用 LangGraph 的 Send API 实现 Map-Reduce 分治——先并发提取各章节要点（Map），再汇总生成全局结论（Reduce）。”

1. 三大超限场景的工程治理方案全景对比

超限来源场景 核心解决策略 工程落地实现细节 优缺点与适用边界
场景 A：
多轮对话与 Agent 循环记忆膨胀		 1. 令牌级滑动窗口裁剪 (trim_messages)
2. 滚动摘要 (SummarizationMiddleware)
3. 外部长期记忆库 (Long-term Store)		 • 保留顶层 SystemMessage + 最近 $N$ 个 Token 的消息。
• 当 Token 超阈值（如 4000），将旧消息总结为摘要并利用 LangGraph RemoveMessage 清理旧节点状态。
• 用户画像与关键事实抽取出存入外部 Vector Store 按需检索。		 生产标配 兼顾近期细节精确性与长周期上下文连贯性，Token 消耗恒定可控。
场景 B：
RAG 召回文档 / Tool 返回巨型 JSON		 1. Rerank 截断 + 父子按需展开
2. 提示词压缩 (Prompt Compression)
3. 上下文卸载 (Context Offloading)		 • 严控注入 LLM 的 Chunk 数量（通常 3~5 块），剔除低分噪声。
• 使用 LLMChainExtractor 或 LLMLingua-2 小模型滤除检索块中的冗余修饰词，仅保留核心事实句。
• 工具返回超长报表时，截断前 2000 字符并附带分页查询工具。		 立竿见影 大幅降低无效 Token 噪声，显著提升模型推理专注度与准确率。
场景 C：
超长单篇文档处理
(百页财报/合同/代码库)		 1. Map-Reduce 并行分治归纳
2. Refine 滚动迭代精炼
3. 层次化索引树 (RAPTOR / 章节摘要树)		 • Map-Reduce：将长文切分为 10 个子段并发调用 LLM 提取子摘要，再由 Reduce 节点合并。
• Refine：带着前一段的结论顺序阅读下一段，适合强前后逻辑依赖的文档。		 高吞吐/高耗时 Map-Reduce 适合可并行汇总的分析；Refine 适合连贯性要求高的长文改写。

2. 为什么“模型窗口够大”依然要做上下文控制？（Lost in the Middle 原理）

面试官常追问：“现在主流模型都支持 128K 甚至 1M 上下文了，直接全塞进去不行吗？” 此时必须从以下三个维度专业反驳：

  • 注意力 U 型衰减效应（Stanford "Lost in the Middle" 论文）：研究表明，大模型对位于上下文最开头（Primacy Bias）和最末尾（Recency Bias）的信息召回率最高，而当有效信息被淹没在长上下文中间位置时，推理准确率会断崖式下跌（甚至低于不带上下文的盲猜）。工程解法：在组装 RAG Prompt 时，采用首尾交替重排（LongContextReorder），把相关性排第 1、2 名的文档放在最开头和最末尾，把排名靠后的放在中间。
  • 延迟与算力成本（Quadratic Attention）：Transformer 自注意力机制在 Prefill 阶段计算复杂度随序列长度呈平方级（$O(N^2)$）或准线性增长，每次携带 50K 历史会导致 TTFT（首 Token 延迟）长达数秒，且每次 API 调用都在为重复历史买单。
  • 工具调用完整性破坏（Tool Call Integrity）：粗暴按字符截断字符串极易把 JSON 结构或一组 AIMessage(tool_calls) -> ToolMessage 拦腰截断，导致 OpenAI / Qwen 接口直接抛出 400 Bad Request (messages with role 'tool' must be a response to a preceding message with 'tool_calls')。

3. 生产级代码实战：安全裁剪 `trim_messages` + 滚动摘要状态机

from langchain_core.messages import SystemMessage, RemoveMessage, trim_messages
from langgraph.graph import MessagesState

def call_model_with_safe_context(state: MessagesState):
    """【方案一】使用 trim_messages 在调用 LLM 前安全裁剪上下文，绝不破坏 Tool Call 配对"""
    trimmed_messages = trim_messages(
        state["messages"],
        max_tokens=4000,
        strategy="last",               # 保留最新消息
        token_counter=llm,             # 使用对应模型的 Tokenizer 精确计费
        include_system=True,           # 强制保留顶层 SystemMessage 指令
        allow_partial=False,           # 严禁截断单条消息内部文本
        start_on="human",              # 确保裁剪后的窗口第一条对话从 HumanMessage 开始，防止孤立的 ToolMessage 报错
    )
    response = llm.invoke(trimmed_messages)
    return {"messages": [response]}

def summarize_conversation_node(state: MessagesState):
    """【方案二】当对话超长时，将早期历史压缩为滚动摘要，并用 RemoveMessage 物理清理旧消息"""
    summary = state.get("summary", "")
    # 仅保留最近 4 条消息原文，将其余早期消息归纳进 summary
    old_messages = state["messages"][:-4]
    prompt = f"已有摘要：{summary}\n请将以下新增历史对话浓缩合并进摘要中，保留关键业务参数与用户偏好：\n{old_messages}"
    new_summary = small_fast_llm.invoke(prompt).content
    
    # 利用 LangGraph 的 RemoveMessage 从状态通道中精准剔除已归档的旧消息
    delete_ops = [RemoveMessage(id=m.id) for m in old_messages]
    return {"summary": new_summary, "messages": delete_ops}

Q3

什么是 RAG？它解决什么问题

核心概念与本质 参数化记忆 vs 非参数化记忆 RAG vs Fine-Tuning
💡 核心速记：RAG（Retrieval-Augmented Generation，检索增强生成）是一种在调用大模型生成答案前，先从外部权威知识库中动态检索相关事实片段并注入上下文（In-Context Learning）的架构范式。它本质上把“大模型的参数化记忆（推理与语言组织能力）”与“外部知识库的非参数化记忆（实时、私域、可溯源事实）”解耦，专门解决原生 LLM 的四大核心痛点：① 事实性幻觉（Hallucination）、② 知识截止与时效滞后（Knowledge Cutoff）、③ 企业私域数据盲区、④ 缺乏答案溯源与细粒度权限管控。
🎙️ 面试 30 秒开口即答（逐字稿背诵版）

“面试官您好，如果把原生大模型比作‘闭卷考试’，那么 RAG（检索增强生成）就是让大模型带着企业的权威参考书去‘开卷考试’。从技术本质上看，大模型的训练权重属于静态的‘参数化记忆’，而 RAG 引入了外部向量库与搜索引擎作为动态的‘非参数化记忆’。它在企业落地中核心解决了四个问题：第一是抑制事实性幻觉，强制模型基于检索到的真实文档作答而非凭概率瞎编；第二是打破知识截止期与高昂的训练成本，比如我们平台的商品价格、库存状态或最新法规每分钟都在变，不可能每次变动都重新预训练或微调模型，而用 RAG 只需毫秒级更新向量库即可实时生效；第三是注入企业专有私域知识，无需将核心机密数据外泄用于训练；第四是提供可解释的引用溯源（Citation）与文档级权限隔离（RBAC），让每一句回答都能定位到具体哪本手册的第几页，满足金融、医疗和电商客服的合规审计要求。”

1. 原生大模型的四大固有缺陷与 RAG 的破局机制

  • 解决痛点一：事实性幻觉（Hallucination） —— 原生 LLM 本质是基于 Token 概率分布做自回归预测，遇到未知的垂直领域细节（如某款二手车型的特殊召回通告）会“一本正经地胡说八道”。RAG 通过将 Ground Truth 事实直接塞进 Prompt，将任务从“凭空回忆”降维成“阅读理解”，大幅压降幻觉率。
  • 解决痛点二：知识时效性滞后（Knowledge Cutoff） —— 预训练模型的知识停留在训练截点，无法感知实时新闻、最新业务政策或动态库存。RAG 只需对增量文档执行 Embedding 入库，即可实现秒级/分钟级知识热更新。
  • 解决痛点三：企业私域数据盲区与数据安全 —— 企业内部 SOP、内部 Wiki、客户档案不在公网训练语料中。RAG 允许数据留在企业本地数据库/向量库内，并在检索层结合用户身份（Role-Based Access Control）过滤出该员工有权查看的片段。
  • 解决痛点四：黑盒不可解释与无法追责 —— 原生模型输出无法给出真实出处。RAG 可在返回答案的同时返回召回块的 source_url、doc_id 与高亮原文，实现 100% 可审计溯源。

2. 面试必考对比：RAG vs 微调（Fine-Tuning / SFT）到底怎么选？

对比维度 RAG（检索增强生成 — 开卷考试） Fine-Tuning（监督微调 SFT — 考前特训） 生产最佳实践（RAFT / 组合拳）
核心目标定位 补充外部动态知识与事实（让模型知道“是什么”）。 内化特定说话风格、输出格式、领域黑话或推理范式（让模型学会“怎么说/按什么格式输出”）。 RAG 管知识，SFT 管格式与路由能力（如微调模型更好地输出 Tool Calling JSON 或忽略噪声文档）。
知识更新频率与成本 秒级/分钟级更新 仅需增删改向量库记录，成本极低。 天级/周级重训 需重新准备语料、租用 GPU 训练并重新部署，且存在灾难性遗忘风险。 高频变化事实走 RAG + 工具调用；固定不变的行业术语理解与垂域指令遵循走 SFT。
幻觉抑制与可追溯性 极强（支持精确角标溯源） 可配置无检索结果时直接拒答。 较弱（仍可能产生幻觉） 知识融于权重黑盒中，无法给出精确文档引用。 医疗、法务、金融、严谨客服等严肃场景必须以 RAG 为底座。
数据权限隔离 (ACL) 原生支持 可按用户角色在检索阶段做 Metadata 过滤。 无法隔离 一旦训练进模型权重，任何能调用该模型的人都可能套出训练数据。 多租户 SaaS 或分级权限知识库只能使用 RAG 实现权限隔离。

3. RAG 架构的三代演进范式（展现技术视野）

1. 【Naive RAG（初代朴素 RAG）】:
   Query ──► Embedding ──► 向量 Top-K 检索 ──► 拼接到 Prompt ──► LLM 生成
   (痛点：切片粗糙、纯向量漏检专有名词、召回噪声直接污染生成结果)

2. 【Advanced RAG（进阶生产级 RAG）】:
   [检索前 Pre-Retrieval]: Query Rewrite / HyDE (假设性文档嵌入) / 路由分发 / 父子切片与元数据注入
   [检索中 Retrieval]:     Dense + Sparse BM25 混合检索 (Hybrid Search)
   [检索后 Post-Retrieval]: RRF 融合 + Cross-Encoder Rerank 精排 + 上下文重排与压缩

3. 【Modular & Agentic RAG（智能体驱动的模块化 RAG — 当前主流）】:
   基于 LangGraph 构建循环状态图（如 Corrective RAG / Self-RAG）：
   Agent 自主判断 Query 是否需要检索 ──► 检索后由 Grader 节点评估文档相关性
   ──► 若不相关则自动触发 Rewrite Query 重新检索或 Fallback 调用 Web Search，直至证据充分再生成答案。

3. 基于 LangGraph 的多智能体协作核心代码（含并行会诊 `Send` 与客服 `Command` 交接）

from operator import add
from typing import Annotated, Literal, TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.types import Command, Send, interrupt

# 1. 定义全局会诊/客服共享状态契约
class MultiAgentState(TypedDict):
    patient_summary: str                                  # 结构化患者病历 / 客服工单摘要
    departments: list[str]                                # 需参与会诊的专科列表
    specialist_reports: Annotated[list[dict], add]        # 并行专科意见经 add Reducer 自动归并
    conflict_detected: bool                               # 药师质控是否发现冲突
    revision_round: int                                   # 协商轮次计数器（防死循环）
    active_agent: str                                     # 客服 Swarm 当前接管 Agent

# 2. 【医疗会诊模式】主治医师通过 Send 动态并行扇出多个专科子智能体 (Map 阶段)
def dispatch_specialists(state: MultiAgentState) -> list[Send]:
    return [
        Send("specialist_agent_node", {"dept": dept, "case": state["patient_summary"]})
        for dept in state["departments"]
    ]

def pharmacist_critic_node(state: MultiAgentState) -> Command[Literal["supervisor_replan", "final_report"]]:
    """【药师质控节点】检查各专科汇总的处方是否存在药物相互作用冲突"""
    has_conflict = check_drug_interactions(state["specialist_reports"])
    if has_conflict and state.get("revision_round", 0) < 2:
        return Command(
            update={"conflict_detected": True, "revision_round": state.get("revision_round", 0) + 1},
            goto="supervisor_replan"  # 打回重新协调剂量
        )
    return Command(update={"conflict_detected": False}, goto="final_report")

# 3. 【智能客服模式】使用 Command 同时更新状态并完成跨 Agent 交接 (Swarm Handoff)
def sales_agent_handoff_to_refund(state: MultiAgentState, order_id: str, reason: str) -> Command[Literal["refund_agent"]]:
    """售前 Agent 识别到售后退货诉求，生成结构化交接单并直接将控制权移交给售后 Agent"""
    handoff_note = f"【跨坐席交接单】订单号：{order_id}，用户诉求：{reason}"
    return Command(
        update={"patient_summary": handoff_note, "active_agent": "refund_agent"},
        goto="refund_agent"
    )
🎯 面试必拿分的三大工程防坑设计： 1. 防上下文雪崩（Context Isolation）：子 Agent 执行完复杂的检索与工具调用后，只把精炼后的结构化结论（Report/Summary）写回父图共享 State，将内部几十条检索草稿留在子图私有状态中销毁； 2. 防无限踢皮球（Anti-Ping-Pong Loop）：在客服 Swarm 交接中，State 必须维护 handoff_count，单次请求跨 Agent 交接超过 3 次立刻强制路由至兜底或人工坐席； 3. 状态黏性（Session Stickiness）：多轮对话中，下一轮用户输入进来时，根据 Checkpointer 记忆的 active_agent 直接路由给当前正在服务他的子 Agent，而不是每句话都重新走顶层分类器。

Q5

文档切片怎么切？切片大小怎么定？

Chunking 策略选型 Parent-Child 父子索引 Chunk Size & Overlap 黄金法则
💡 核心速记： ① 怎么切（按文档形态分级治理）：通用文本首选结构化标题切分（Markdown/HTML Header）+ 递归字符切分（RecursiveCharacterTextSplitter）；高价值复杂文档采用父子分层切片（Parent-Child：小块检索引擎算相似度、大块喂给大模型保语义）；长篇无格式文本采用语义断点切分（Semantic Chunking）或延迟分块（Late Chunking）；表格与代码块严禁拦腰切断。 ② 切片大小怎么定（四大决定因素）：取决于Embedding 模型最大窗口与甜点区、用户 Query 粒度（事实点查询 vs 宏观总结）、文档信息密度、以及重排/生成 Token 预算。生产黄金经验值：检索块（Child）定在 256 ~ 512 Tokens（中文约 350~600 字），重叠率（Overlap）定在 10% ~ 20%（约 50~100 Tokens），生成父块（Parent）定在 1024 ~ 2048 Tokens。
🎙️ 面试 45 秒开口即答（结合项目调优数据背诵版）

“面试官您好，文档切片的本质是在‘检索向量的语义纯粹度（块越小越聚焦）’与‘生成上下文的语义完整性（块越大背景越全）’之间做权衡。在实际项目中，我们绝不用一刀切的定长切分，而是采用‘结构化感知 + 父子双层索引（Small-to-Big）’方案：首先在怎么切上，我们先将 PDF/Word 解析为带层级标题的 Markdown，第一层先用 MarkdownHeaderTextSplitter 按章节标题切出 1200~1500 字的父块（Parent Chunk）保证逻辑完整，第二层再在父块内部用 RecursiveCharacterTextSplitter 按段落、句号、分号优先级递归切出 400 字左右、重叠 50 字（约 12% Overlap）的子块（Child Chunk），并在每个子块头部拼上章节标题和文档元数据前缀，解决跨段指代丢失问题；对于文档中的表格，我们单独提取为 Markdown Table 或 JSON 行并生成自然语言摘要，绝不拆碎表头。其次在切片大小怎么定上，我们依据四个维度实测校准：① Embedding 模型的最佳表征甜点区（如 bge-large / text-embedding-v3 在 256~512 Tokens 时向量信噪比最高，超过 1000 字向量会被均值池化稀释）；② 业务问题类型（精确参数查询用 256~512 Tokens，政策流程问答依靠回表父块补充到 1500 字）；③ 结合 RAGAS 离线评测集跑网格实验（对比 256 / 512 / 1024 下的 Context Recall 与 Faithfulness），最终定下‘子块 400 字检索 + 父块 1500 字生成’的黄金组合。”

1. 六大主流文档切片（Chunking）策略选型全景表

切片策略名称 核心切分原理 核心优势 局限性与适用文档场景
1. 固定长度切分
(Fixed-size Chunking)		 机械按每 $N$ 个字符/Token 硬切，配固定滑动窗口 Overlap。 实现最简单，计算开销几乎为零。 生产慎用 极易把完整句子、表格或代码拦腰斩断，造成严重语义残缺。
2. 递归字符切分
(RecursiveCharacter)		 按分隔符优先级列表 ["\n\n", "\n", "。", "！", "？", "；", " "] 自顶向下递归切分，直到块小于目标阈值。 最大程度尊重自然段落与句子边界，性价比最高。 通用基座标配 适合大多数常规文本文档、FAQ 与规章制度。
3. 文档结构感知切分
(Markdown / HTML / AST)		 按 Markdown 的 # / ## / ### 标题树、HTML DOM 标签或代码语法树（Class/Function）切分。 天然保留章节归属关系，可将各级标题自动提取进 metadata。 技术手册/SOP首选 适合结构规范的技术文档、API 手册、法律条文与代码库。
4. 父子分层索引
(Parent-Child / Small-to-Big)		 用细粒度子块（如 300 字）建向量索引保证高相似度命中；命中后通过 parent_id 取出大父块（如 1500 字）喂给 LLM。 完美解耦“检索要准（块小）”与“生成要全（块大）”的矛盾！ 企业级生产黄金方案 适合长篇业务手册、质检规范、医疗指南与复杂合同。
5. 语义断点切分
(Semantic Chunking)		 计算相邻句子 Embedding 的余弦距离，当语义突变超过百分位阈值（如 95%）时在此处切开。 不依赖排版格式，确保每个 Chunk 内部讨论的是同一个高内聚主题。 构建耗时较高 离线构建需对每句话算向量；适合缺乏标点/标题排版的会议转录稿或长访谈。
6. 上下文增强与延迟分块
(Contextual Retrieval / Late Chunking)		 切块后调用低成本模型（结合 Prompt Caching）为每个块生成 50 字全局背景前缀；或先过长窗口 Embedding 再按 Token 池化。 彻底解决子块脱离原文后“主语/指代丢失”（如块内只写“它的保修期为3年”，不知“它”是谁）。 高阶提分利器 显著降低顶层检索失误率，适合高价值核心知识库。

2. 切片大小（Chunk Size）与重叠度（Overlap）到底怎么定？

当面试官问“切片大小怎么定”时，切忌只报一个死数字，必须先讲权衡曲线（Trade-off），再给场景化参考表：

  • Chunk Size 太小（如 < 128 Tokens）的弊端：向量表征虽然极度聚焦，但丢失了前因后果与主语指代（Context Fragmentation），即使检索命中了，LLM 看着半句话也无法推理出完整答案。
  • Chunk Size 太大（如 > 1024 Tokens）的弊端：一段话里包含多个不同主题，经过 Embedding 模型均值池化（Mean Pooling）后，向量特征被严重“稀释平均化”（Semantic Dilution），导致与具体问题的余弦相似度反而下降，且浪费生成端 Token 预算。
  • Overlap（重叠窗口）定多少：通用法则是 Chunk Size 的 10% ~ 20%（例如 400 字配 50~80 字 Overlap），作用是防止关键过渡句刚好落在切分边界上被一劈为二。

表格密集型文档（财报 / 车型参数表） 整表独立 或 按 N 行带表头切分 重复携带表头行 (Header Row) 切分超长表格时，每个子块第一行必须强制保留 Markdown 表头；同时用 LLM 生成一段文字描述该表核心指标用于向量检索。

3. 生产级代码实战：结构化标题感知 + 中文标点递归切分 + 上下文注入

from langchain_text_splitters import MarkdownHeaderTextSplitter, RecursiveCharacterTextSplitter

def split_enterprise_document(md_text: str, doc_title: str):
    # 第一步：按 Markdown 章节标题树切分，保留天然的业务语义边界与层级 Metadata
    headers_to_split_on = [
        ("#", "h1"),
        ("##", "h2"),
        ("###", "h3"),
    ]
    md_splitter = MarkdownHeaderTextSplitter(headers_to_split_on=headers_to_split_on, strip_headers=False)
    header_docs = md_splitter.split_text(md_text)

    # 第二步：针对中文语料定制分隔符优先级，在章节内部递归切分细粒度检索块
    recursive_splitter = RecursiveCharacterTextSplitter(
        chunk_size=450,
        chunk_overlap=60,  # 约 13% 重叠度，防止句群边界语义断裂
        separators=["\n\n", "\n", "。", "！", "？", "；", "，", " ", ""],
    )
    child_chunks = recursive_splitter.split_documents(header_docs)

    # 第三步：Contextual Header Injection（将文档标题与章节路径注入块首，解决指代丢失）
    for chunk in child_chunks:
        breadcrumb = " > ".join(
            filter(None, [doc_title, chunk.metadata.get("h1"), chunk.metadata.get("h2"), chunk.metadata.get("h3")])
        )
        chunk.page_content = f"【所属章节：{breadcrumb}】\n{chunk.page_content}"
    return child_chunks
