Q1

集成 MCP 之后，Agent 调用工具的链路是怎样的？

MCP 协议链路 JSON-RPC 2.0 tools/list & tools/call
💡 核心速记：集成 MCP（Model Context Protocol） 后，Agent 调用工具由传统的“进程内硬编码函数直调”演进为基于 JSON-RPC 2.0 的“Host ➔ MCP Client ➔ MCP Server”标准六步链路：① 初始化握手协商（initialize） ➔ ② 工具发现与 Schema 转换（tools/list） ➔ ③ LLM 意图决策输出 tool_calls ➔ ④ 客户端路由与高危拦截（HITL） ➔ ⑤ 跨进程/跨网络协议调用（tools/call） ➔ ⑥ 结果封装 ToolMessage 回写 State 并生成最终回答。
🎙️ 面试 35 秒开口即答（逐字稿背诵版）

“面试官您好，集成 MCP 之后，Agent 不再直接耦合具体业务工具的 SDK，而是通过 Host（宿主 Agent 编排器）— MCP Client — MCP Server 三层标准链路基于 JSON-RPC 2.0 完成闭环，全链路分为 6 步：第一步是握手与工具发现，Agent 启动或会话初始化时，MCP Client 与各业务 MCP Server 完成 initialize 能力协商，并发送 tools/list 请求拉取工具名称、描述和 JSON Schema，通过 Adapter（如 langchain-mcp-adapters）动态绑定给大模型；第二步是模型决策，用户提问后，LLM 结合上下文和注入的 Tool Schema 生成结构化的 tool_calls 指令（包含工具名和参数）；第三步是路由与协议执行，LangGraph 的 ToolNode 拦截到调用指令，由对应的 MCP Client 封装成标准的 tools/call JSON-RPC 报文，通过本地 Stdio 管道或远程 Streamable HTTP / SSE 传输层发往目标 MCP Server；第四步是服务端执行与上下文回填，MCP Server 执行查库或调外部 API，将返回的 content 或 structuredContent 原路返回给 Client，封装为 ToolMessage 追加进 LangGraph 的 State，最后再次驱动 LLM 汇总生成自然语言答复流式推给前端。”

2. 六大核心阶段协议级深度拆解（面试追问必背细节）

链路阶段 核心动作与 JSON-RPC 2.0 协议方法 关键工程实现细节（答出即拿高分）
1. 握手与能力协商
(Initialization)		 Client 发送 initialize 请求，Server 返回 {"capabilities": {"tools": {"listChanged": true}}}，随后 Client 发送 notifications/initialized。 声明 listChanged: true 后，若后端动态上下线工具，Server 会主动推送 notifications/tools/list_changed，Client 自动重新拉取无需重启 Agent。
2. 工具发现与转换
(Discovery)		 Client 调用 tools/list（支持 cursor 游标分页与 ttlMs 缓存），获取各工具的 name、description、inputSchema（JSON Schema 2020-12）。 确定性排序缓存优化：Server 严格按固定顺序返回工具列表，确保拼入大模型 System Prompt 时前缀完全一致，大幅提升 LLM Prompt Cache（KV Cache）命中率。
3. 命名空间防冲突与权限过滤 当聚合多个 MCP Server 时（如订单 Server 与知识库 Server 都有 search 工具），Adapter 自动为工具加上服务前缀（如 order__search）。 工具列表支持基于请求级 Token Scope 动态裁剪（只向当前用户暴露其权限范围内的工具），杜绝越权展示。
4. 大模型推理决策
(Tool Selection)		 LangGraph 的推理节点将用户消息与转换后的 StructuredTool 列表传给 LLM，模型返回 AIMessage(tool_calls=[{"name": "...", "args": {...}}])。 条件边 tools_condition 检测到 tool_calls 非空，将控制流路由至 ToolNode（高危工具先过 interrupt() 人工审批节点）。
5. 协议调用与传输执行
(Invocation)		 Client 发送 tools/call 请求（携带 name 和 arguments）。底层支持 Stdio（本地子进程标准输入输出）或 Streamable HTTP（含 SSE 流式响应）。 在远程 Streamable HTTP 下，支持通过 Schema 中的 x-mcp-header 注解将关键参数（如 region）自动映射为 HTTP 头 Mcp-Param-Region，方便 API 网关按分片路由。
6. 结果校验与状态回写
(Observation)		 Server 返回 content（文本/图片/嵌入资源 URI）与符合 outputSchema 的 structuredContent，以及 isError 标志位。 若 isError: true，Client 不会直接抛出未捕获异常崩掉进程，而是将错误详情包装进 ToolMessage 写回 State，让大模型在下个超步自主修正参数重试！

3. LangGraph 集成多 MCP Server 标准生产代码范式

from langchain_mcp_adapters.client import MultiServerMCPClient
from langgraph.graph import StateGraph, MessagesState, START, END
from langgraph.prebuilt import ToolNode, tools_condition
from langchain.chat_models import init_chat_model

llm = init_chat_model("openai:gpt-4o")

async def run_mcp_agent(user_query: str, thread_id: str):
    # 1. 连接多个异构 MCP Server（同时支持本地 Stdio 与远程 Streamable HTTP）
    async with MultiServerMCPClient({
        "vehicle_db": {
            "url": "https://internal-mcp.company.com/vehicle/mcp",
            "transport": "streamable_http",
            "headers": {"Authorization": "Bearer <service-token>"}
        },
        "rag_knowledge": {
            "command": "python",
            "args": ["./mcp_servers/milvus_rag_server.py"],
            "transport": "stdio"
        }
    }) as mcp_client:
        # 2. 底层自动发送 JSON-RPC `tools/list`，并将 JSON Schema 转换为 LangChain StructuredTool
        mcp_tools = mcp_client.get_tools()
        llm_with_tools = llm.bind_tools(mcp_tools)

        async def agent_node(state: MessagesState):
            response = await llm_with_tools.ainvoke(state["messages"])
            return {"messages": [response]}

        # 3. 构建 LangGraph 状态图，ToolNode 内部自动通过 MCP Client 发送 `tools/call`
        builder = StateGraph(MessagesState)
        builder.add_node("agent", agent_node)
        builder.add_node("tools", ToolNode(mcp_tools))
        builder.add_edge(START, "agent")
        builder.add_conditional_edges("agent", tools_condition)
        builder.add_edge("tools", "agent")

        graph = builder.compile()
        return await graph.ainvoke({"messages": [("user", user_query)]})
🎯 面试进阶加分项（MCP 多轮补全机制 input_required）：在最新版 MCP 规范中，当工具执行发现缺少必填凭证或需要用户二次确认时，MCP Server 在 tools/call 响应中可直接返回 "resultType": "input_required" 与 elicitation/create 表单 Schema 及加密的 requestState，前端收集用户输入后带上 inputResponses 与 requestState 重试即可无缝续接，极大简化了有状态工具的交互实现。

Q2

简单介绍下 MCP 协议，它在你们项目里解决了什么核心问题？

AI 应用的 USB-C M×N 降维 M+N 跨语言微服务解耦
💡 核心速记：MCP（模型上下文协议） 是连接 AI 应用与外部数据源/工具的开源开放标准（如同 AI 界的 USB-C 接口），对外统一暴露 Tools（工具）、Resources（资源）、Prompts（提示词模板） 三大原语。在项目中它主要解决了四大核心痛点：① 消除 $M \times N$ 重复适配胶水代码（实现一次开发多智能体复用）、② 打通 Python Agent 编排层与 Java 核心业务微服务的跨语言壁垒、③ 将高危工具与数据库凭证从 Agent 进程中物理隔离（安全沙箱与独立扩缩容）、④ 支持工具 Schema 动态热发现与统一网关审计。
🎙️ 面试 40 秒开口即答（结合项目实战逐字稿背诵版）

“面试官您好，MCP（Model Context Protocol，模型上下文协议）是标准化大模型应用与外部数据、工具交互的开放协议，基于 JSON-RPC 2.0 构建，可以把任何外部系统统一抽象成 Tools（函数调用）、Resources（只读数据上下文）和 Prompts（标准工作流模板） 三类能力，相当于给 AI 应用装上了统一的 USB-C 扩展坞。在我们项目里，引入 MCP 主要解决了三个原本非常头疼的工程痛点：第一是解决了‘跨团队、多 Agent 重复造轮子’的 $M \times N$ 集成难题——以前我们导购 Agent、售后客服 Agent 和内部运营助手都要查订单库、查车况档案和向量库，每个 Agent 都要自己写一套 Tool 封装和参数校验，后端接口一改所有 Agent 全得跟着发版；改成 MCP Server 后，各业务域只维护一套标准 MCP 接口，所有 Agent 即插即用；第二是解决了‘Python 编排层与 Java 业务微服务异构割裂’的问题——我们核心交易和风控微服务是 Spring Boot 技术栈，而复杂智能体编排在 LangGraph，通过 Spring AI MCP Server 与 LangGraph MCP Client 对接，彻底抹平了跨语言 RPC 与 Schema 同步成本；第三是解决了‘权限泄露与进程故障传染’问题——把数据库连接池和第三方私钥完全收敛在各自的 MCP Server 容器内，Agent 宿主进程只拿受限 Token 发起调用，哪怕某个外部工具超时OOM，也不会拖垮核心 Agent 状态机。”

1. MCP 协议核心架构与三大标准原语

根据 MCP 官方架构文档，MCP 采用经典的客户端-服务端解耦架构，由 MCP Host（AI 应用程序，如自研 Agent 中台、Claude Desktop、Cursor）、MCP Client（宿主内维护与单一 Server 1:1 连接的协议组件）与 MCP Server（对接数据库、API 或本地文件的轻量服务）组成，并定义了三大标准原语：

  • Tools（工具 — Model-controlled 模型控制）：供 LLM 自主决策调用的可执行函数（如查询实时库存、创建工单、执行 SQL），具备严格的 JSON Schema 输入输出约束。
  • Resources（资源 — Application-controlled 应用控制）：类似 REST 里的 GET 只读数据源，以统一 URI（如 postgres://db/schema、file:///logs/error.log）向模型提供结构化背景知识，支持订阅变更通知。
  • Prompts（提示模板 — User-controlled 用户控制）：服务端预置的标准化 Prompt 模板与 Few-shot 工作流（如“线上慢 SQL 诊断模板”），前端可直接映射为斜杠命令（Slash Commands）供用户一键触发。

2. 引入 MCP 前后：项目工程痛点解决对比表

业务与工程痛点维度 引入 MCP 之前（传统硬编码 Function Calling） 引入 MCP 之后（标准化 MCP 架构）
1. 多 Agent 工具复用度
($M \times N$ vs $M + N$)		 耦合严重 $M$ 个 Agent 接入 $N$ 个内部系统需编写 $M \times N$ 套胶水适配器；后端字段变更需多处同步修改。 即插即用 降维至 $M + N$：每个业务域只暴露 1 个标准 MCP Server，所有 Agent、评测脚本、IDE 调试器直接复用。
2. 异构技术栈协同
(Java + Python)		 维护繁琐 需手写 REST 接口文档，再在 Python 端手写一套 Pydantic Schema 和 requests 封装，极易出现双端类型不一致。 Schema 自动对齐 Java 微服务通过 Spring AI 注解直接暴露 MCP Server，Python LangGraph 启动时通过 tools/list 自动拉取生成 Tool Schema。
3. 安全性与凭证隔离
(Security & Blast Radius)		 高危集中 Agent 进程需配置所有下游 MySQL、Redis、第三方 API 的 AK/SK，且工具代码异常会直接导致 Agent 进程崩溃。 沙箱解耦 数据库账密完全封装在各领域 MCP Server 内部，Agent 仅传递用户级 OAuth/JWT 凭证，故障爆炸半径严格隔离。
4. 可观测性与版本演进
(Governance)		 分散杂乱 各工具调用日志格式不一，难以统一统计耗时、成功率与限流。 统一网关治理 基于标准 JSON-RPC 报文与 Mcp-Param-* 请求头，在网关层统一实现工具级 QPS 限流、审计日志与熔断降级。

3. 生产落地中的架构治理细节（防追问亮点）

  • 长连接池化与工具 Schema 缓存：避免每次用户对话都重新触发 initialize + tools/list 网络往返，我们在 MCP Client 层维护长连接会话池，并利用协议返回的 ttlMs 将 Tool Schema 缓存在内存中，仅在收到 notifications/tools/list_changed 时增量刷新。
  • 大体积返回截断与 Resource 引用转换：如果某个 MCP 工具查询返回了上万行日志或超长 JSON，直接塞回 ToolMessage 会瞬间撑爆 LLM 上下文窗口。我们在 MCP Server 层做了统一规范：超过 4KB 的大结果仅在 ToolResult 中返回摘要 + resource_link URI，Agent 确需查看明细时再按分页拉取。

Q3

你们项目里 Agent 的流式输出是怎么实现的？用的什么方案？

LangGraph astream v2 SSE 多事件分帧 Fetch ReadableStream
💡 核心速记：我们采用“LangGraph 多模式异步流（stream_mode=["messages", "updates", "custom"]） + 后端 SSE（text/event-stream）自定义事件分帧 + 前端 fetch + ReadableStream 流式解码 + AbortController 中断控制”的全链路方案。不仅实现最终回答的打字机逐 Token 输出，还能实时流式推送思维链节点切换状态、MCP 工具执行进度条与人工审批挂起事件。
🎙️ 面试 45 秒开口即答（逐字稿背诵版）

“面试官您好，因为 Agent 跟普通单次大模型对话不同，它中间要经历意图路由、RAG 检索、MCP 工具调用等多个步骤，如果只流式输出最后一段文字，前面几秒钟用户界面会完全卡死白屏。所以我们项目落地的是‘多维事件流（Multi-mode Event Streaming）+ SSE 协议分帧’的全链路方案，具体分三层实现：第一层在 LangGraph 编排层，我们调用 graph.astream(..., stream_mode=['messages', 'updates', 'custom'], subgraphs=True, version='v2')：用 updates 模式捕获每个节点的进出状态，向前端推送‘正在检索知识库’、‘正在调用估价工具’等步骤状态；用 custom 模式配合节点内的 get_stream_writer() 推送长耗时工具的百分比进度；用 messages 模式捕获大模型逐 Token 生成，并通过给内部打分/路由模型打上 nostream 标签（或按 langgraph_node 过滤），确保只把面向用户的最终回答 Token 流推给前端。第二层在网关与服务端传输层，用 FastAPI 的 StreamingResponse 将不同事件封装成带 event: step / token / tool / done 的标准 SSE 格式，同时加上 X-Accel-Buffering: no 响应头禁用 Nginx 缓冲，并每 15 秒发一次注释心跳防网关断连。第三层在前端交互层，因为原生 EventSource 不支持带 JSON Body 的 POST 请求和自定义鉴权 Header，我们用 fetch 配合 ReadableStream + TextDecoder 逐块解析 SSE 事件流，并绑定 AbortController 实现一键停止生成。”

1. 全链路三层流式架构与 SSE 事件分帧协议设计

为了让前端 UI 既能丝滑展示“思考过程步骤折叠面板（Reasoning Steps）”，又能实时渲染“打字机文本流（Token Stream）”与“结构化业务卡片（Artifact Card）”，我们在 LangGraph Streaming v2 基础上定义了标准化的 5 类 SSE 事件帧：

SSE 帧类型 (event:) 对应 LangGraph stream_mode 来源 负载格式示例 (data: JSON) 前端 UI 渲染动作
event: step stream_mode="updates" {"node": "rag_retrieve", "status": "completed", "doc_count": 4} 更新顶部“思考与工具调用步骤条”图标状态（转圈 ➔ 绿色对勾）。
event: progress stream_mode="custom"
(get_stream_writer())		 {"tool": "mcp_car_Inspect", "msg": "已核验 180/259 项质检指标", "pct": 70} 在当前工具步骤卡片内实时刷新进度条，彻底消除长耗时工具等待焦虑。
event: token stream_mode="messages" {"delta": "根据检测报告，该车...", "node": "final_answer"} 追加到 Markdown 增量渲染器中，实现 60fps 丝滑打字机输出。

2. 核心工程细节：如何避免“内部思考 JSON”泄漏到前端流？

在多节点 Agent 图中，很多中间节点（如 Query 重写节点、文档相关性打分节点 grade_documents）也会调用 LLM。如果直接开启 stream_mode="messages"，这些内部节点的 JSON 输出也会一股脑流向前端用户聊天框！我们采用 LangGraph 官方推荐的双重过滤机制完美解决：

  1. 声明式静默标签（tags=["nostream"]）：对仅用于内部结构化判断、重写或打分的 LLM 实例绑定 model.with_config({"tags": ["nostream"]})，LangGraph 运行时会自动在 messages 流中屏蔽其 Token 产出。
  2. 消费端节点白名单过滤（metadata["langgraph_node"]）：在遍历 chunk["type"] == "messages" 时，检查 msg_chunk, metadata = chunk["data"] 中的 metadata.get("langgraph_node")，仅当属于面向用户的生成节点（如 final_responder）且不包含 tool_call_chunks 时，才封装为 event: token 下发。

3. 生产级全链路代码实战（后端 FastAPI SSE + 前端 Fetch 流式消费）

import asyncio, json
from fastapi import FastAPI, Request
from fastapi.responses import StreamingResponse

app = FastAPI()

def format_sse(event: str, data: dict) -> str:
    return f"event: {event}\ndata: {json.dumps(data, ensure_ascii=False)}\n\n"

@app.post("/api/v1/agent/chat/stream")
async def stream_agent_chat(req: Request, body: dict):
    config = {"configurable": {"thread_id": body["thread_id"]}}

    async def event_generator():
        try:
            # 开启 v2 统一流格式，同时订阅 messages (Token)、updates (节点状态) 与 custom (自定义进度)
            async for part in graph.astream(
                {"messages": [("user", body["query"])]},
                config=config,
                stream_mode=["messages", "updates", "custom"],
                subgraphs=True,
                version="v2"
            ):
                # 1. 客户端断开连接检测（如用户点击“停止生成”）
                if await req.is_disconnected():
                    break

                ptype = part["type"]
                pdata = part["data"]

                # 2. 处理 LLM 逐 Token 流（过滤掉工具调用参数拼接块与内部节点）
                if ptype == "messages":
                    msg_chunk, meta = pdata
                    if meta.get("langgraph_node") == "final_answer" and msg_chunk.content:
                        yield format_sse("token", {"delta": msg_chunk.content})

                # 3. 处理节点完成状态更新
                elif ptype == "updates":
                    for node_name, node_state in pdata.items():
                        yield format_sse("step", {"node": node_name, "status": "done"})

                # 4. 处理节点/工具内通过 get_stream_writer() 主动发射的进度数据
                elif ptype == "custom":
                    yield format_sse("progress", pdata)

            yield format_sse("done", {"thread_id": body["thread_id"]})
        except asyncio.CancelledError:
            # 释放底层连接与计算资源
            raise
        except Exception as e:
            yield format_sse("error", {"message": "服务繁忙，请稍后重试", "detail": str(e)})

    return StreamingResponse(
        event_generator(),
        media_type="text/event-stream",
        headers={
            "Cache-Control": "no-cache, no-transform",
            "Connection": "keep-alive",
            "X-Accel-Buffering": "no",  # 关键：严禁 Nginx 反向代理缓冲攒批！
        }
    )
⚠️ 生产环境必踩的 2 个大坑（面试主动提出来极度加分）：
  • 坑 1：本地流式很丝滑，一上生产经过 Nginx 就变成“卡顿 10 秒后一次性蹦出来” —— 原因是 Nginx 默认开启了 proxy_buffering on，会把后端的小块响应攒够缓冲区大小才下发。解法：除了在后端代码返回头加 X-Accel-Buffering: no，还要确认云 CDN / WAF 关闭了响应 Gzip 压缩缓冲（或加 Cache-Control: no-transform）。
  • 坑 2：前端用 TextDecoder 解码流时偶发中文乱码（） —— 原因是 UTF-8 一个汉字占 3 字节，网络分包可能把一个汉字截断在两个 Uint8Array chunk 之间。解法：前端调用 decoder.decode(value, { stream: true }) 必须显式传入 { stream: true }，让解码器自动缓存末尾不完整的字节序列拼到下一包解码！

Q4

为什么选 SSE 做 Agent 流式，而不是 WebSocket？

架构选型权衡 SSE vs WebSocket HTTP/2 多路复用
💡 核心速记：选 SSE（Server-Sent Events） 而非 WebSocket 的本质原因是：AI Agent 对话是典型的“非对称半双工场景（一次短请求触发长周期单向流式下发）”。SSE 直接运行在标准 HTTP/HTTPS 之上，具备① 完美契合业务通信模型、② 零成本复用现有 HTTP 网关/鉴权/负载均衡基础设施、③ 无状态易水平扩展、④ 原生支持事件分帧与 `Last-Event-ID` 断点续传、⑤ 与 OpenAI / Anthropic / MCP 等上下游生态同构五大压倒性优势。
🎙️ 面试 35 秒开口即答（逐字稿背诵版）

“面试官您好，我们在架构选型时对比过这两者，最终坚定选择 SSE 主要基于四个维度的工程权衡：第一是通信模型匹配度，Agent 文本交互的本质是‘客户端低频发一条指令，服务端高频单向流式推送 Token 与步骤状态’，根本不需要 WebSocket 的全双工并发上行能力，用 WebSocket 属于典型的架构过载；第二是基础设施与网关兼容性，SSE 本质就是普通的 HTTP 长响应（Content-Type: text/event-stream），可以直接复用我们现有的 Spring Cloud Gateway / Nginx 路由、Bearer Token 鉴权拦截器、WAF 防火墙和全链路 Trace，而 WebSocket 需要 101 Switching Protocols 协议升级，在企业级多层反向代理和云函数网关下非常容易掉线且难以做无状态负载均衡；第三是生态同构性，目前上游的大模型厂商（OpenAI、Claude、通义千问）以及下游的 MCP Streamable HTTP 协议全线采用 SSE，前后端统一用 SSE 可以做到端到端流式透传，无需做额外的协议转换；第四是容错成本，SSE 规范原生自带 event: 事件分类与 id:（Last-Event-ID）断线续传机制，而在 HTTP/2 多路复用普及后，早期 HTTP/1.1 同域 6 个连接的限制也早已不复存在。”

1. SSE 与 WebSocket 在 AI Agent 场景下的六维对比矩阵

对比维度 SSE (Server-Sent Events / fetch Stream) WebSocket (ws:// / wss://)
底层传输协议 标准 HTTP / HTTPS 无需协议升级，完全遵循常规 HTTP 请求-响应生命周期。 独立 WS 协议 需通过 HTTP 101 Switching Protocols 握手升级为独立 TCP 帧通道。
通信方向与业务契合度 单向服务端推送（请求-流式响应）：100% 契合 LLM“一问一答持续吐字”与“停止生成（Abort）”模式。 全双工双向通道：适合高频双向通信（如弹幕/音视频流/协同白板），在文本 Agent 场景下 90% 上行通道闲置。
网关、鉴权与防火墙穿透 零改造兼容 直接走现有 API 网关、JWT Header 鉴权、CORS、WAF 与 K8s Ingress，企业内网防火墙无阻碍。 运维成本高 需单独配置网关 Upgrade 头、长连接空闲超时与代理穿透，且标准浏览器 WS API 不支持自定义 Authorization Header。
水平扩缩容与状态管理 请求级有界生命周期 单次回答完毕连接即释放，下一次提问可路由至任意 Pod（配合 Checkpointer 完全无状态扩展）。 持久有状态长连接 用户打开页面即占住连接，滚动发版或扩容时面临连接迁移、跨节点广播（需 Redis Pub/Sub）与僵尸连接清理难题。
断点续传与协议语义 协议原生内置 原生支持 event: 分类、id:（Last-Event-ID）与 retry:，网络抖动重连可按偏移量续传。 全靠手写实现 仅提供裸字节/文本帧，心跳保活（Ping/Pong）、断线重连退避、消息序号对齐全需业务层自己造轮子。
AI 上下游生态一致性 全链路同构 OpenAI/Anthropic API、LangGraph Server、MCP Streamable HTTP 均以 SSE 为标准。 需协议桥接 后端拿到上游 LLM 的 SSE 流后，还需再转封装一层 WebSocket 帧下发。

2. 面试官常见反问：“听说 SSE 有同域名 6 个连接数限制，且不支持 POST，你们怎么解决的？”

这是面试官检验你是否真正写过生产级 Agent 前后端的高频追问，标准满分回答如下：

  • 追问 1：原生 new EventSource(url) 只支持 GET 请求，没法传大段 Prompt JSON Body，也没法带自定义 Authorization: Bearer 请求头，怎么破？
    👉 解法：在生产环境中，我们服务端遵循 SSE 规范（text/event-stream），但前端并不使用老旧的 new EventSource()，而是使用现代浏览器的 fetch(url, { method: 'POST', headers: {...}, body: JSON.stringify(...) }) 配合 response.body.getReader()（或 @microsoft/fetch-event-source 库）。这样既保留了 POST 传复杂参数和标准 Header 鉴权的能力，又完全享受了 SSE 的文本流协议优势！
  • 追问 2：MDN 文档提到 SSE 在浏览器里有最大 6 个并发连接限制，多开几个标签页会卡死吗？
    👉 解法：6 个连接的限制仅存在于古老的 HTTP/1.1 协议下（因为 HTTP/1.1 每个 SSE 独占一条 TCP 连接）。现在我们的线上网关与 Ingress 全部开启了 HTTP/2（及 HTTP/3），所有 SSE 流在底层共享同一条 TCP 连接进行多路复用（Multiplexing，默认单连接并发流上限为 100+），早已不存在多标签页阻塞问题。

3. 辩证架构视野：什么场景下我们会改用 WebSocket？

🎯 面试收尾加分话术（体现不唯技术论的架构师思维）： “当然，我们并不是一刀切排斥 WebSocket。在两个特定场景下我们会选用 WebSocket（甚至 WebRTC）： ① 全双工实时语音交互 Agent（如 GPT-4o Realtime API 语音通话）：用户在说话的同时 Agent 也在下发音频流，且需要毫秒级语音打断（Barge-in），这时必须用全双工长连接； ② 客户端与 Agent 实时协同编辑画布（高频双向状态同步）。但对于 95% 以上的对话式、工作流式与多模态卡片式 Agent，HTTP/2 + POST SSE 是兼具开发效率、网关兼容性与云原生弹性的最优解。”

你们 Agent 的会话记忆是怎么实现的？用的什么存储方案？

Checkpointer + Store Redis + PostgreSQL + pgvector 滑动窗口与摘要裁剪
💡 核心速记：基于 LangGraph Persistence 双层记忆体系，我们将 Agent 记忆拆分为“短期单会话工作记忆（Short-Term Checkpointer）”与“长期跨会话用户记忆（Long-Term Store）”，底层采用“Redis 7.0（热态高速缓存） + PostgreSQL（状态快照与冷备落盘） + Milvus / pgvector（长期语义记忆向量检索）”三级存储方案，并配合“滑动窗口保留最近 $K$ 轮 + 异步滚动摘要（Rolling Summary） + 工具消息成对裁剪”防止上下文溢出。
🎙️ 面试 45 秒开口即答（逐字稿背诵版）

“面试官您好，我们项目的会话记忆没有采用早期把历史消息全塞进 Redis List 然后硬拼 Prompt 的粗放做法，而是基于 LangGraph 构建了‘短期线程记忆（Checkpointer）+ 长期跨会话记忆（Store）+ 上下文窗口治理’的三位一体方案。在存储选型与分层架构上：第一层是短期会话内记忆（Short-Term Memory），按会话 thread_id 隔离，用于保存当前对话的多轮上下文和图状态快照。我们采用 Redis + PostgreSQL（AsyncPostgresSaver） 双写/热冷分层：活跃会话近 2 小时的 Checkpoint 走 Redis 保障 5 毫秒以内的极速读写，同时异步落盘 PostgreSQL 保障持久化和历史会话恢复；第二层是长期跨会话记忆（Long-Term Memory），按用户 user_id 命名空间隔离，用来记住用户的个人画像、预算偏好和历史关键事实。我们在每轮对话结束后通过异步后台任务提炼用户画像写入 LangGraph Store（底层基于 PostgreSQL pgvector / Milvus 支持语义向量检索），当用户新开一个会话时，先语义召回 Top-K 长期记忆注入 System Prompt；第三层是上下文防爆治理，当单次会话超过 12 轮或 Token 逼近阈值时，自动触发滚动摘要（Rolling Summary）把早期对话压缩成一段 summary 存入 State，并用 RemoveMessage 或 trim_messages 裁剪旧消息（严格保证 AIMessage(tool_calls) 与 ToolMessage 成对保留，防止大模型接口报 400 错误）。”

2. 存储引擎选型与职责划分矩阵

存储组件 在记忆体系中的角色 具体存储结构与表设计 为什么选它？（选型理由）
Redis 7.0 Cluster 热态短期记忆加速层 & 会话并发锁 缓存最近活跃 thread_id 的最新 Checkpoint 序列化快照（TTL=2h）；以及 lock:thread:{id} 防止同一会话并发连点导致状态错乱。 内存级读写延迟（< 2ms），完美支撑多轮高频连续追问场景下的极速状态加载。

3. 核心工程难点：长对话 Token 裁剪与滚动摘要实战代码

如果用户在一个会话里聊了 50 轮，state["messages"] 列表会越来越长，不仅推理变慢、费用剧增，还会触发上下文超限。我们在图中设计了“滚动摘要（Rolling Summary）+ 安全消息裁剪”机制：

from langchain_core.messages import SystemMessage, RemoveMessage, trim_messages
from langgraph.graph import StateGraph, MessagesState, START, END
from langgraph.checkpoint.postgres.aio import AsyncPostgresSaver
from langgraph.store.postgres.aio import AsyncPostgresStore

# 扩展 MessagesState，增加 rolling_summary 字段保存压缩后的历史摘要
class ChatMemoryState(MessagesState):
    rolling_summary: str

async def call_model_with_memory(state: ChatMemoryState, config, *, store):
    user_id = config["configurable"].get("user_id")
    # 1. 【长期记忆召回】从跨会话 Store 中按语义检索该用户的历史偏好
    user_memories = await store.asearch(("memories", user_id), query=state["messages"][-1].content, limit=3)
    mem_text = "\n".join([m.value["fact"] for m in user_memories])

    # 2. 【短期记忆组装】将历史滚动摘要 + 长期记忆拼入 System Prompt
    sys_content = f"你是一名专业AI助手。\n【用户长期偏好】：{mem_text}\n"
    if state.get("rolling_summary"):
        sys_content += f"【前序对话摘要】：{state['rolling_summary']}"

    # 3. 【安全滑动窗口裁剪】使用 trim_messages 限制送入模型的最大 Token，且绝不拆散 ToolCall 与 ToolMessage！
    trimmed_msgs = trim_messages(
        state["messages"],
        max_tokens=4000,
        strategy="last",
        token_counter=llm,
        start_on="human",      # 确保裁剪后的第一条消息是 HumanMessage，防止孤立的 ToolMessage 引发 400 报错
        include_system=False,
    )
    response = await llm.ainvoke([SystemMessage(content=sys_content)] + trimmed_msgs)
    return {"messages": [response]}

async def summarize_and_prune_node(state: ChatMemoryState):
    """当消息条数超过阈值（如 14 条）时，压缩早期对话为摘要，并从 State 中物理移除旧消息"""
    if len(state["messages"]) <= 14:
        return {}
    old_msgs = state["messages"][:-6]  # 保留最近 6 条原始消息，压缩更早的消息
    summary_prompt = f"原有摘要：{state.get('rolling_summary', '无')}\n请结合新增对话更新精简摘要：{old_msgs}"
    new_summary = (await summary_llm.ainvoke(summary_prompt)).content
    # 使用 RemoveMessage 从 add_messages 通道中精确删除已归档的早期消息
    delete_ops = [RemoveMessage(id=m.id) for m in old_msgs]
    return {"rolling_summary": new_summary, "messages": delete_ops}
🎯 面试必杀加分项（生产踩坑细节）：
  1. 为什么裁剪消息时必须加 start_on="human"？ 因为在 Agent 场景下，一轮问答里往往包含 AIMessage(tool_calls=[...]) 紧跟着 ToolMessage(tool_call_id=...)。如果简单按条数切片（如 messages[-10:]），极易把前面的 AIMessage 切掉、只留下孤立的 ToolMessage，此时调 OpenAI / 通义千问接口会直接抛出 400 Bad Request: messages with role 'tool' must be a response to a preceding message with 'tool_calls'！
  2. Checkpoint 表膨胀治理：根據 LangGraph Persistence 生产指南，thread_id 长度需严格限制在 255 字符以内（推荐 UUIDv7），且我们配置了定时归档任务（Cron Job），对超过 30 天未活跃的会话只保留最新 1 个 Checkpoint 快照并清理历史中间步骤快照，防止 checkpoint_blobs 表无限膨胀。
