Q1

结合业务说一下 RAG 流程，从离线知识库构建、在线检索召回、大模型生成三个阶段讲。

💡 面试官意图剖析：这是一道「验真题」。面试官不想听「先切分、再向量化入库、然后检索、最后生成」这种教科书复述——那种回答一听就是背的。他想确认三件事：① 你是否真的负责过链路上的某一环；② 每个阶段你做了什么具体的技术决策；③ 你用什么指标判断这个阶段做得好不好。所以回答必须绑定具体业务场景（企业知识助手 / 售后工单 / HR 制度问答），每个阶段抛 2~3 个真实工程动作 + 1 个踩坑点。

1.1 阶段一：离线知识库构建（决定 RAG 的上限）

业务背景（开口先给场景，再讲技术）： 我们做的是企业级知识助手，服务客服与内部员工。知识源包括产品手册 PDF、售后 SOP、历史工单、HR 制度文档，累计约 1.2 万份文档 / 300 万字，并且带两个硬约束：部门权限隔离（销售看不到研发文档）和版本时效性（旧版制度必须失效）。这两点直接决定了后面索引结构怎么设计。

🧠 一句话定调：
离线阶段解决的是「这段知识到底能不能被召回」——知识没被正确解析、正确切块、正确打标，在线阶段再花哨的算法也救不回来。所以我们团队 60% 的调优时间其实花在离线侧。
环节 我们的做法 工程细节与踩过的坑
① 数据接入与解析 多格式统一解析：PDF / Word / Excel / PPT / 扫描件 文本层用 Unstructured 做版面分析，扫描件走 PaddleOCR；Excel 转 Markdown 保留表头，避免整表被切碎；坑点：双栏 PDF 直接按行提取会把左右栏串行，必须按 block 坐标排序
② 清洗与降噪 页眉页脚 / 页码 / 目录 / 水印 / 乱码清理，SimHash 去重 同一份制度存在多版本副本，用 SimHash 做近重复检测后只保留最新版并归档旧版；坑点：目录页被当成正文入库，用户问「第三章讲什么」时召回的是一堆页码
③ 结构化分块 结构感知切分（标题层级）+ Parent-Child 双层块 Child 块 256~512 token 用于向量检索（语义聚焦），Parent 块约 1500 token 用于喂给大模型（上下文完整）；overlap 64 token 防止跨段语义断裂
④ 元数据注入 部门权限、生效时间、文档版本、来源 URL、标题路径面包屑 标题路径（售后制度 > 退换货 > 七天无理由）直接拼到块文本前缀，显著提升短 query 的召回命中性
⑤ 向量化 bge-large-zh-v1.5 / 百炼 text-embedding-v3（1024 维） 批量接口 + 幂等增量：以文档 doc_hash 判断是否变化，只重跑变更文档，全量重建一次要 3 小时，增量降到 6 分钟
⑥ 索引落库 Milvus（或 ADB-PG）向量索引 + ES 倒排索引双写 HNSW 参数 M=16, efConstruction=200；双写是为了后面做混合检索；用 collection alias 切换实现无感重建
⑦ 调度与版本 每日 T+1 定时增量任务，软删除 + 别名切换 过期文档不物理删，打 is_valid=false 标记，检索时统一加时间过滤，保证历史问答可追溯

1.2 阶段二：在线检索召回（决定答案的上限）

在线链路我通常会画成四层：Query 理解 → 多路召回 → 融合重排 → 上下文组装。用户在一句话里可能只说了「它的保修期呢」，指代、错别字、口语化全都得在这一层消化掉。

Layer 1 · Query 理解

把用户问题变「可检索」

  • 多轮指代消解： 「它 / 这个型号」回填为完整实体，否则向量检索直接跑偏。
  • 术语归一： 「保内」「保修期内」「质保」统一映射到同一标准词表。
  • 意图路由： 先判断是不是知识类问题；闲聊或纯算术直接走轻量模型，不做无谓检索，省 token 也省延迟。
Layer 2 · 多路召回

向量 + 关键词 + 元数据

  • Dense： 向量检索取 Top-50，负责语义泛化（问法和原文不一致也能召回）。
  • Sparse： BM25 取 Top-50，负责型号、编号、金额、条款号这类精确匹配。
  • 元数据先过滤： 权限部门 + 生效时间作为 pre-filter，先卡范围再算相似度，避免召回越权内容后再丢弃。
Layer 3 · 融合与精排

RRF 融合 + Cross-Encoder 重排

  • RRF 倒数排名融合： 两路结果用排名而非分数融合，规避量纲不可比问题。
  • 重排序： bge-reranker-v2-m3 对 Top-50 精打细算，输出 Top-5。
  • 阈值兜底： 精排分低于 0.35 直接判「无有效召回」，走转人工话术，绝不硬答。
Layer 4 · 上下文组装与缓存

父子块还原 + 语义缓存

  • Small-to-Big： 命中的是 Child 块，但取回它对应的 Parent 块喂模型，兼顾精准与完整。
  • 语义缓存： Redis + 向量相似度 > 0.95 且实体一致即命中，高峰期拦掉 30% 以上重复提问。
  • 可观测： 每次请求落库 query、召回 docId、各路分数、最终引用，支撑 badcase 复盘。

1.3 阶段三：大模型生成与工程护栏（决定可信度）

检索给了「原料」，生成阶段要做的是让模型只能基于原料说话。我们的 Prompt 结构是固定四段：角色设定 → 任务约束 → 检索上下文（带 [1][2] 编号）→ 输出格式，其中约束里必须写死三条：只依据给定资料作答、资料不足时明确说「知识库暂未收录」、禁止编造条款号与数字。

流式输出与首字体验 SSE
全链路打通 Server-Sent Events + 前端渐进式 Markdown 渲染，把用户感知的首字延迟从 3.5s 压到 600ms 以内。检索与重排阶段异步并行，不让用户干等。
引用溯源（Grounding） 可验证
强制模型在每句结论后标注来源编号 [1]，前端渲染为可点击锚点并高亮原文。这一招既是防幻觉，也是给业务方建立信任的关键——客服敢把答案直接转给客户。
结构化输出与自愈重试 JSON Schema
需要驱动下游系统时，用 Structured Outputs / Function Calling 锁定 JSON Schema，后端 Pydantic 校验；校验失败时把错误堆栈回灌给模型做一次自动纠错重试，把格式失败率从 8% 降到 0.5% 以内。
后置护栏与评估闭环 LLMOps
输出侧做敏感词、长度与忠实度校验；离线侧维护 200+ 条 Golden Dataset，用 Ragas 的 Faithfulness / Answer Relevancy / Context Recall 做回归。线上 badcase 每周归因分类，反向回灌到离线分块与检索参数，形成数据飞轮。
✅ 三阶段的一句话总结（面试时直接抛，非常加分）：
离线构建决定「知识能不能被召回」，在线检索决定「召回得准不准」，大模型生成决定「答得可不可信」。三者是乘法关系，任何一环掉链子，最终效果都会断崖式下跌。

1.4 端到端口述模板（建议 2~3 分钟讲完）

Oral Response Script 「我拿我们企业知识助手这个项目来讲，整个 RAG 分成离线、在线、生成三段。」

第一段，离线知识库构建。 知识源是产品手册、售后 SOP、历史工单和 HR 制度，大概 1.2 万份文档，最大的特点是有权限、有版本时效。所以我们的流程是解析 → 清洗去重 → 结构化分块 → 打元数据 → 向量化 → 双索引落库。这里有两个关键决策：一是用标题层级 + Parent-Child 而不是定长切分，子块 512 token 用来检索、父块 1500 token 用来喂模型；二是把标题路径作为面包屑拼进块文本，同时把部门权限和生效时间做成元数据，后面检索时做前置过滤。另外向量化做了幂等增量，靠 doc hash 判断变更，重建从 3 小时降到 6 分钟。

第二段，在线检索召回。 分四层：Query 理解层先做多轮指代消解和术语归一，再判断意图需不需要检索；召回层走 Dense 向量 Top-50 + BM25 Top-50 的混合召回，权限和时效做 pre-filter；融合层用 RRF 把两路排名合并，再用 Cross-Encoder 重排模型 打细分，留 Top-5；组装层做 Small-to-Big 还原父块，并加一层语义缓存。我们还设了分数阈值兜底——精排低于 0.35 就判定无有效召回，直接转人工，绝对不硬答。

第三段，大模型生成。 Prompt 固定四段式，强制模型只能依据检索资料作答，并在结论后标注引用编号，前端可点回原文。工程上做了 SSE 流式、结构化输出 + 校验重试、敏感词与忠实度后置校验。最后是评估闭环：我们有 200 多条 Golden Dataset，用 Ragas 指标做回归，线上 badcase 每周归因，质量问题反向回灌到离线分块和检索参数上持续迭代。
Q2

怎么解决上下文超过大模型限制的问题？

💡 面试官意图剖析：这题分水岭很明显。初级回答只有一句「换更大的模型」或者「截断」；中级回答知道要「滑动窗口 + 摘要」；高级回答会先区分「硬限制」和「有效窗口衰减」两个完全不同的概念，然后给出输入侧压缩 → 调用侧分治 → 模型侧选型 → 工程侧预算兜底的四层治理体系，并坦白说明各自的代价。注意：面试官大概率会追问「那你为什么不用 1M 上下文的模型一把梭」，一定要准备好答案。

2.1 先分清问题本质：硬限制 vs 有效窗口衰减

很多人把这两个混为一谈，但它们的处理方式完全不同。我在项目里是分开治理的：

问题类型 典型表现 本质原因 治理方向
硬限制（Hard Limit） 接口直接报 400 InvalidParameter: Range of input length should be [1, 32768]，请求失败 输入 token 数超过模型窗口上限，物理上放不下 必须压缩或分治，属于功能性问题
有效窗口衰减（Lost in the Middle） 请求成功，但长文中间段落的信息被忽略，答案只用到开头和结尾的内容 注意力在长序列上分布不均，中间信息权重下降 不是「塞得下就行」，而是质量与成本问题
成本与延迟恶化 输入从 2k 涨到 30k，费用翻十几倍，TTFT 从 600ms 涨到 5s+ token 数与费用、延迟近似线性相关 属于经济性问题，需要预算控制
⚠️ 核心认知（这句话建议原样说出来）：
我们的目标从来不是「把窗口塞满」，而是「用最少的 token 携带最有效的信息」。上下文越长，成本越高、延迟越大、准确率还未必更好，所以长上下文是手段而不是目标。

2.2 输入侧瘦身：压缩与记忆管理（性价比最高的一层）

手段一 · 检索结果压缩

少而精，而不是多而全

  • Top-K 收敛： 重排后只留 Top-5，而不是把 Top-20 全塞进去；实测召回片段从 20 条降到 5 条，答案质量反而上升。
  • 句子级抽取压缩： 对每个片段按与 query 的相关度保留核心句，长片段可压缩 40% 以上且几乎不丢信息。
  • 提示压缩： 极端场景用 LLMLingua 类工具做 token 级压缩，可压到原长度的 1/3~1/5，代价是有信息损失风险，需要回归验证。
手段二 · 历史记忆管理

滑动窗口 + 递归摘要

  • 分层记忆： 最近 3 轮保留原文（粗粒度细节最重要），更早的轮次压成摘要，摘要硬限制 300 token 以内。
  • 递归摘要： 摘要本身也超限时，对摘要再摘要，避免无限膨胀。
  • 只带一次： 指代消解后把历史信息合并进当前 query，历史消息不再重复全量带入。
手段三 · 提示词瘦身

Few-Shot 动态挑选

  • 动态示例： 从示例池按语义相似度 kNN 挑 2~3 条最相关的，而不是固定堆 10 条通用示例。
  • 规则外置： 大量业务规则改为代码侧路由判断，只把当前场景相关的规则注入 Prompt。
  • 格式精简： 用紧凑 JSON 替代冗长的自然语言示例描述，能省下可观 token。
手段四 · 先摘要后问答

Map-Reduce 预压缩

  • 面对「把这份 80 页手册总结一下」这类需求，先把文档分段摘要成一页精华，再基于摘要做多轮问答。
  • 摘要结果落缓存，同一份文档的后续追问不再重复计算。

2.3 调用侧分治、预算控制与模型选型

如果输入侧压完还是超限，就得靠调用策略来解决。这里我准备了四套方案，按场景切换：

Map-Reduce 分治：长文摘要、批量抽取 并行处理
把长文切成多个可独立处理的段，并行调用模型得到分段结果（Map），再用一次调用归并（Reduce）。坑点：Reduce 阶段本身也可能超限，所以 Map 的输出必须限长；并行调用要配并发限流。
Refine 迭代精炼：有时间顺序 / 需要连贯性的任务 串行保序
逐段处理并把上一段结果作为下一段输入，天然保持叙事连贯，适合长文改写、跨章节推理。代价：串行导致延迟线性增长，所以只在对连贯性有硬要求的场景用。
分段生成 + 续写拼接：长文输出 突破输出上限
让模型先输出分段大纲，再逐段生成后拼接。关键在于每段结尾要把已生成内容的关键信息带回去，避免重复和断裂，最后加一次一致性校对。
长上下文模型选型：按需付费，不无脑上 Qwen-Long / 128k
确实需要全量文档推理时（如合同比对、跨文档交叉验证），用 Qwen-Long（百万级）或 128k 窗口模型。但我会先算账：长窗口单价更高、TTFT 更长，能用 RAG 精排解决的场景绝不走全量入参。

最后是工程侧的硬预算兜底（这一层最能体现工程素养）：

✅ 调用前的 Token 预算校验与降级链路：
  • 预计算： 用 tiktoken / 厂商 tokenizer 在组装 Prompt 前先算长度，公式为 可用输入预算 = 窗口上限 − max_tokens（输出预留） − 10% 安全余量，绝不「试出来才报错」。
  • 按优先级截断： 一旦超限，按 System 约束 > 最近一轮原文 > 高精排分检索片段 > 早期摘要 的顺序裁剪，保证核心约束和最新意图永远不丢。
  • 自动降级： 触发截断时打埋点告警并降级到「摘要模式」或更小上下文重试，而不是直接把报错抛给用户。
  • 效果验证： 每次调整预算策略都跑一遍 Golden Dataset，确认截断没有带来质量回退。

2.4 场景决策矩阵与口述模板

检索片段堆太多 重排收敛 Top-5 + 句子级抽取 约 -60% 依赖重排质量，重排差则丢信息
超长文档总结 / 抽取 Map-Reduce 分段并行 理论上不限 跨段关联信息易丢，需 Reduce 设计好
跨章节连贯改写 Refine 迭代精炼 理论上不限 串行调用，延迟显著上升
跨文档交叉比对 长上下文模型（Qwen-Long） 不降反增 成本高、首字慢，需评估 ROI
Oral Response Script 「这个问题我会先区分两种情况：是真超了报错，还是没超但效果变差。」

如果是硬限制，我的治理顺序是「先压缩、再分治、最后才换模型」。压缩这一层性价比最高：检索结果用重排收敛到 Top-5 再做句子级抽取，历史对话用滑动窗口加递归摘要，把早期多轮压成 300 token 以内的摘要，Few-Shot 也改成按语义动态挑 2~3 条。这样一通下来，我们线上平均输入 token 降了大概 70%，成本和首字延迟都明显改善。

如果压完还放不下，就走调用侧分治：长文摘要和批量抽取用 Map-Reduce 并行分段，需要跨章节连贯的用 Refine 串行迭代，长文输出就先出大纲再分段生成拼接。真的需要全量文档推理时，才会上 Qwen-Long 这类长窗口模型，但一定会先算成本账。

最重要的是硬预算兜底：我们在组装 Prompt 之前就用 tokenizer 预计算长度，按「窗口 − 输出预留 − 10% 余量」算可用预算，按 System 约束、最新轮次、片段分数的优先级截断，并埋点告警、自动降级到摘要模式。不能让超限变成线上 400 报错，这是最基本的工程底线。

另外补充一点，即使窗口没满，长上下文里中间段落的信息也会被稀释，就是常说的 Lost in the Middle。所以我们的判断标准不是「塞不塞得下」，而是「这些 token 是不是真的带来了信息增益」。
Q3

你们知识库检索这块，采用的是什么样的策略？

💡 面试官意图剖析：这题是 Q1 的「下钻题」，面试官想确认你在检索环节真的调过参、做过对比实验，而不是直接调了某个框架的默认 similarity_search。回答的黄金结构是：「为什么不能只用向量 → 我们用了什么组合 → 每一层的取舍 → 用什么指标证明它有效」。如果能把 RRF 的公式和阈值兜底的数值说出来，可信度会瞬间拉满。

3.1 核心策略：混合检索（Hybrid Retrieval），为什么不能只用向量

我们最早也是纯向量检索起步的，但在真实业务里踩到了三个明确的短板，这也是后来必须引入 BM25 的原因：

向量检索的短板一

专有名词与编码匹配不准

  • 型号 KX-3200A、工单号、SKU 编码这类 OOV 短语，embedding 空间里没有稳定语义，相似度容易漂移。
  • 用户把 KX-3200A 打成 kx3200a 时，向量召回可能跑到完全无关的文档。
向量检索的短板二

精确数字与条款失效

  • 「违约金是千分之三还是千分之五」这类问题，需要的是精确字面匹配，向量会把语义相近但数字不同的段落一起召回。
  • 条款号「第 7.2.3 条」用向量检索几乎必然误召回。
向量检索的短板三

超短 Query 语义漂移

  • 用户只输入「发票」「报销」两个字时，向量信息量不足，Top-K 结果发散严重。
  • 这类短 query 用 BM25 反而非常稳定。
BM25 的互补价值

字面精确、可解释、零训练成本

  • 对编码、数字、条款号的精确匹配能力是向量无法替代的。
  • 得分可解释，方便排查「为什么召回了这条」。
  • 不需要 GPU，倒排索引查询延迟极低。

结论：向量负责「语义泛化」（问法和原文表述不同也能召回），BM25 负责「字面精确」（编码、数字、专有名词）。两者是互补而非替代关系，所以我们最终走的是双路混合召回。

3.2 多路召回与 RRF 融合：为什么用排名融合而不是加权求和

两路召回各取 Top-50 之后，怎么合并是门学问。我们试过加权分数求和，很快放弃了，原因是向量相似度（0~1 的余弦值）和 BM25 分数（无上界的实数）量纲完全不可比，归一化后仍然受分布影响，调权重极其痛苦且不稳定。

📐 我们最终采用 RRF（Reciprocal Rank Fusion，倒数排名融合）：

RRF_score(d) = Σ 1 / (k + rank_i(d))，其中 k = 60（经验平滑常数），rank_i(d) 是文档 d 在第 i 路召回中的排名（从 1 开始，未召回则忽略该路）。

  • 只依赖排名，不依赖分数： 彻底规避跨模型分数量纲问题，两路谁都不需要迁就谁。
  • 天然的多路投票机制： 同时被两路召回的文档排名会前进，符合「多路都认为是好结果」的直觉。
  • 鲁棒： 某一路召回质量下降时，整体不会崩，这在生产环境非常重要。

融合后我们会做一次去重（同一父块的多个子块只保留最高分的一个），再进入重排环节。

3.3 两阶段重排与 Query 侧优化

先说重排。 向量检索用的是 Bi-Encoder——query 和 doc 各自独立编码后算余弦相似度，快但精度有限，因为两者在编码阶段从未交互。而 Cross-Encoder 把 query 和 doc 拼在一起送进模型，能捕捉词级交互，精度显著更高，代价是无法预先建索引，只能对候选集在线打分。

对比项 Bi-Encoder（召回层） Cross-Encoder（精排层）
工作方式 Query 与 Doc 独立编码，离线可索引 Query + Doc 拼接后联合编码打分
处理规模 全库百万级（毫秒级） 仅候选 Top-50（百毫秒级）
精度 语义泛化好，细粒度排序弱 细粒度排序强，是质量提升的主力
我们的用法 混合召回取 Top-50 重排后取 Top-5 喂模型
实测增益 — 答案准确率 +7pt 左右，延迟增加约 80~150ms

再说 Query 侧优化，这是投入产出比极高但经常被忽略的一层：

优化一 · 查询改写

Query Rewriting

  • 指代消解： 结合多轮历史把「它 / 这个」还原成完整实体。
  • 术语归一： 维护业务同义词表，把口语映射到标准术语。
  • 纠错补全： 修正错别字与拼音误输入。
优化二 · 多查询扩展

Multi-Query

  • 用小模型把原 query 改写成 2~3 个不同表述，并行召回后取并集。
  • 对口语化、模糊提问提升明显，代价是召回量翻倍、延迟略增。
  • 只对短 query 或首次无召回的情况触发，控制成本。
优化三 · HyDE

假设性文档嵌入

  • 让模型先「编」一段假设答案，再用这段答案去检索。
  • 因为假设答案的表达更接近文档语气，能显著提升 recall。
  • 适合专业术语密集的场景，但会引入一次额外模型调用。
优化四 · 意图路由

该不检索就不检索

  • 寒暄、算术、纯格式转换类请求直接跳过检索。
  • 省 token、降延迟，同时避免无关片段污染上下文。

3.4 参数工程、元数据过滤与效果评估（体现「可量化」）

元数据先过滤后检索（Pre-filter）： 这点在企业场景是刚需，不只是效果问题，更是权限安全问题。我们把部门可见性、文档生效时间、密级做成过滤条件，在向量检索前就限定范围。如果在检索后再过滤，会出现「Top-5 里 4 条都是越权文档，被过滤后只剩 1 条」的尴尬局面——召回率直接崩塌。

✅ 我们线上固化的一组关键参数（可以直接报数）：
  • 召回路数： Dense Top-50 + Sparse Top-50，RRF k=60。
  • 重排输入/输出： Top-50 → Top-5，精排分数阈值 0.35 以下判定为无有效召回。
  • 向量索引： HNSW，M=16、efConstruction=200、查询时 ef=64（在召回率与延迟间取平衡）。
  • 兜底策略： 无召回时返回固定话术并转人工，同时记录 no_recall 埋点，每周复盘。

评估指标（面试时务必给出指标名，不要只说「效果变好了」）：

指标 含义 我们的用法
Recall@5 标准答案片段是否出现在 Top-5 中 离线评测主指标，直接反映检索能力天花板
MRR 首个相关结果排名的倒数均值 衡量「好的结果有没有排在前面」，指导重排调参
NDCG@5 考虑排序位置与相关度分级 多档相关度标注场景使用
无召回率 线上触发兜底话术的请求占比 线上监控核心指标，超过 8% 立即排查分块与词表
引用点击率 / 点踩率 用户是否点开引用、是否点踩 真实用户反馈信号，用于发现离线评测覆盖不到的 badcase
Oral Response Script 「我们检索这块的策略可以概括成一句话：多路混合召回 + RRF 融合 + 两阶段重排 + Query 侧优化，外面再包一层权限与时效过滤。」

第一层是召回。 我们最早纯向量，后来发现三类问题搞不定：型号编码、精确数字条款、还有「发票」这种两个字的超短 query。BM25 在这三类上非常稳，所以改成了向量 Top-50 加 BM25 Top-50 的双路召回。

第二层是融合。 我们没用加权求和，因为余弦相似度和 BM25 分数根本不是一个量纲，调权重调到崩溃。最后用的是 RRF 倒数排名融合，只看排名不看分数，公式是每个文档在所有路里的 1/(60+rank) 求和，稳定且天然具备多路投票的效果。

第三层是精排。 召回用的是 Bi-Encoder，query 和 doc 分开编码，没有交互，所以精度有限；精排换成 Cross-Encoder 重排模型，把两者拼起来联合打分，从 Top-50 收敛到 Top-5。这一层带来的准确率提升大概 7 个百分点，代价是增加 100 毫秒左右的延迟，我们认为非常划算。

第四层是 Query 侧和过滤。 多轮场景先做指代消解和术语归一，短 query 触发 Multi-Query 扩展；权限和生效时间做成 pre-filter 提前过滤，而不是检索完再筛——否则 Top-5 里可能四条都是越权文档，召回率直接崩。

最后我们设了分数阈值 0.35 兜底，低于这个分就判定无有效召回，转人工，宁可说「不知道」也不硬答。效果上我们盯 Recall@5、MRR 这些离线指标，线上则重点看无召回率和点踩率。
Q4

你对比过其他的分块策略吗？你们这个分块方式在准确率上有多少提升？

💡 面试官意图剖析：这是典型的「数据打假题」。面试官要验证你的提升数字是评测出来的还是编出来的。高分回答的固定套路是：① 先列举你实际对比过的策略（证明广度）→ ② 说明你的评测集怎么建的、用什么指标（证明可信）→ ③ 给出分层的数据（证明深度）→ ④ 主动补充局限性和不同语料的差异（证明不是拍脑袋）。第 ④ 步是绝大多数候选人不会做的，做了会非常加分。

4.1 主流分块策略全景图（先show广度）

分块策略我基本都试过或至少做过小规模验证，按「从简单到复杂」大致可以分成这样几类：

策略 核心思路 优点 局限
固定长度分块 按 token 数硬切，如每 512 token 一刀 实现最简单、成本最低、块长均匀 会在句子中间切断，语义碎片化严重
递归字符分块 按 \n\n → \n → 。 → 空格 逐级回退切分 通用性最好，天然避免断句 不理解文档结构，跨章节内容会被混在一块
结构感知分块 按 Markdown / Word 标题层级切，保留章节边界 语义完整度最高，块内主题一致 依赖文档有规范结构，纯文本工单收益有限
语义分块（Semantic Chunking） 计算相邻句 embedding 相似度，在突变处切分 切分点最贴合语义，泛化性强 需要全量算 embedding，成本与耗时高，块长不可控
Parent-Child / Small-to-Big 小子块用于检索，命中后返回父块用于生成 同时兼顾检索精准度与生成上下文完整 需要维护双层索引，存储与逻辑复杂度上升
句子窗口（Sentence-Window） 以句为单位检索，命中后带上前后 N 句 命中粒度最细，噪声最低 句子级向量数量爆炸，索引规模成倍增长
Late Chunking 先让长文整体过 embedding 模型，再对 token 向量池化切分 保留了长程上下文，块向量含全局信息 对模型与推理框架有要求，工程改造量大
Contextual Retrieval 用 LLM 为每个块生成一句「它在文档中的位置与作用」并前置 显著缓解块脱离上下文导致的误召回 入库时每个块多一次 LLM 调用，成本明显上升
Agentic / 语义单元分块 由模型判断逻辑单元边界（如一个完整流程、一张表） 最贴近人的阅读单元，效果上限高 成本最高、速度最慢，难以支撑海量文档

4.2 我们最终落地的方案与实现细节

综合效果、成本和工程复杂度，我们最终选的是 「结构感知分层切分 + Parent-Child 双层块 + 块级语境增强」，并针对特殊内容做了专门处理：

决策一 · 结构优先，兜底递归

按标题树切，没结构才回退

  • 文档解析后先构建标题层级树，尽量让一个块 = 一个完整小节。
  • 单个小节超过 512 token 时，再用递归字符分块二次切分，保证不硬断句。
  • 超短小节（< 80 token）向上合并到同级相邻块，避免产生无信息量的碎片。
决策二 · Parent-Child 双层

小块检索，大块生成

  • Child 256~512 token： 做向量检索，语义聚焦、区分度高。
  • Parent 约 1500 token： 命中 Child 后返回其父块喂模型，上下文完整。
  • 维护 parent_id 映射，检索结果去重时按父块聚合。
决策三 · 块级语境增强

面包屑 + 一句话定位

  • 把标题路径（售后制度 > 退换货 > 七天无理由）拼到块文本前缀。
  • 对关键制度类文档，用 LLM 生成一句「本块描述的是 XX 场景下的 XX 规则」前置，用于对齐问法。
  • 实测对短 query 的召回提升最明显，因为块里补齐了缺失的语境词。
决策四 · 特殊内容专门处理

表格、代码、流程不切碎

  • 表格： 转 Markdown 并整表保留为一块，绝不从中间断开；大表按行分组但重复表头。
  • 代码 / 配置： 按函数或配置段整体保留，不按行数硬切。
  • 流程步骤： 编号步骤视为一个整体，缺失任一步都会导致答案错误。
🔧 参数不是拍脑袋定的，是网格搜索出来的：
我们在 256 / 512 / 1024 三个 chunk size 和 0 / 64 / 128 三档 overlap 上做了 9 组对照实验。结论：512 + overlap 64 在 Recall@5 上最优；256 时召回更精准但上下文过于碎片化、生成质量下降；1024 时噪声明显增多、MRR 反而下滑。

先说评测怎么做的，数据才有说服力：

贡献一 · 混合检索

约 +7~8pt

主要来自型号编码、精确数字类问题的召回修复，这部分是纯向量完全覆盖不到的盲区。

贡献二 · 分块策略本身

约 +10~12pt（本题重点）

从固定切分换成结构感知 + Parent-Child，是提升幅度最大的一环。原因是块内语义变纯了，向量区分度提高；同时父块还原保证了生成时的信息完整。

贡献三 · 重排 + 语境增强

约 +7pt

重排把相关度最高的片段提到前面，语境增强补上了块缺失的定位信息。

补充说明 · 局限性

不是万能药

这些数字是我们团队内部评测集上的结果，不同语料、不同标注口径下绝对数值会有差异，我更看重的是趋势和归因——分块策略是 RAG 里投入产出比最高的环节之一，值得花时间做对照实验，而不是直接沿用框架默认值。

4.4 权衡踩坑与口述模板

坑点一：小块召回准，但上下文太碎 用 Parent-Child 解
早期把 chunk 调到 256，检索确实准了，但模型经常因为缺前文而答不完整。Parent-Child 正是为了解决这个矛盾——用小块保证召回精度，用父块保证生成完整度。
坑点二：overlap 不是越大越好 成本换收益
overlap 从 64 加到 128，召回略有提升，但索引体积、检索耗时和重复结果比例都上升，去重逻辑压力变大。最终停在 64，属于甜蜜点。
坑点三：表格是最容易翻车的地方 整表保底
一张保修改价表被从中间切开，导致模型只能看到部分型号的价格，回答出现严重错误。后来强制表格整表成块，并重复表头，这个问题彻底消失。
坑点四：不要迷信某一种策略 A/B 实测
语义分块在公开评测上很亮眼，但在我们工单语料上收益有限，反而因为 embedding 计算成本高拖慢了每日增量任务。最终只在制度手册这类长文档上启用，其余走结构感知。
Oral Response Script 「对比过，而且我们是做了对照实验才有结论的。」

先说对比范围。 我们横向试了五类：固定长度分块、递归字符分块、语义分块、句子窗口，以及 Parent-Child 父子块。大致的结论是：固定长度最省事但断句严重；递归字符是通用默认值，但没有结构意识；语义分块效果不错但 embedding 成本高、块长不可控；句子窗口粒度最细但索引规模膨胀。

再说评测怎么做。 这是我觉得最容易被忽略的地方。我们从真实工单和客服会话里抽了 200 条问题，人工标注标准答案所在的原文档片段，覆盖单跳、多跳、表格数字和否定条款四类题型。检索侧看 Recall@5 和 MRR，生成侧看答案正确率和幻觉率。实验严格控变量，每次只改一个因素。

然后是数据。 基线是固定 512 加纯向量，Recall@5 是 68.5%，答案正确率 61%。加上混合检索后到 76.2%；换成结构感知分块加 Parent-Child 之后跳到 84%；最后再叠加 Cross-Encoder 重排和块级语境增强，达到 Recall@5 91.5%、答案正确率 88%。

关键归因。 这 23 个点不是分块一个因素带来的，拆开看：混合检索大概 7~8 个点，分块策略本身贡献最大，大约 10~12 个点，重排加语境增强约 7 个点。

最后我想补充一句客观的。 这些数字来自我们自己的业务评测集，不是公开榜单。语料结构越规范，结构感知分块的收益越大；如果是纯口语化的聊天记录，可能拿不到这么多提升。所以我的经验是：不要直接沿用框架默认的分块参数，一定要在自己语料上做对照实验，同时警惕把多个变量的效果算到分块一个因素头上。
Q5

我们公司上班地点离你现在有点远，你怎么考虑的？

💡 面试官意图剖析：这是披着「通勤」外衣的稳定性压力测试。面试官真正想确认的是三件事：① 你入职后会不会因为通勤太远而在试用期离职（招聘成本很高）；② 你是否提前认真想过这个问题，有没有可落地的方案（考察解决问题的习惯）；③ 你对这份工作的意愿到底有多强（是否只是海投）。注意：这题不是让你抱怨，也不是让你立刻谈条件，更不是让你撒谎说「很近很方便」——一旦被发现，信任直接归零。

5.1 应答三原则与回答结构

原则一 · 真诚承认，不回避

先接住问题，再给方案

直接说「确实比较远，单程大概 X 分钟」，比含糊其辞更让人放心。面试官最怕的是你嘴上说没问题、入职两周就受不了。

原则二 · 给可落地方案

搬家 / 租房 / 交通方式

给出你已经想过的具体安排，让面试官相信你把这事当成一个待解决的问题，而不是一个待爆的雷。

原则三 · 锚定长期与稳定性

把通勤换算成投入意愿

明确表达「我更看重岗位成长与团队，通勤是可以自己解决的代价」，把话题重新拉回你的职业选择逻辑上。

回答结构（四步）

认同 → 说明 → 方案 → 表态

① 认同你的顾虑；② 说清我的实际距离和通勤方式；③ 给出我已准备好的一到两个解决方案；④ 表明我对这份工作的长期意愿。

5.2 分场景应答模板（挑一个最贴近你真实情况的）

场景 A：你完全可以接受 —— 打算搬家 / 租房 ⭐ 最推荐
适用：你确实愿意为这份工作调整住处。
核心话术：「我算过，单程大概一小时十分钟。这个距离对我来说是可接受的，因为我已经计划在公司附近租房，快的话入职前两周就能安顿好。我上一份工作也经历过通勤调整，所以对这块有心理预期。相比通勤时间，我更在意团队做的事情和成长空间，这也是我今天坐这么远来面试的原因。」
场景 B：需要公共交通 / 弹性措施的配合 务实型
适用：你不打算搬家，但想确认下弹性工时、班车或混合办公。
核心话术：「距离确实比以前远一些，我查过地铁加步行大概一个半小时。我目前的方案是早高峰提前出门，同时也想了解一下咱们这边上下班时间是否有一定弹性，方便我错峰通勤。如果公司有班车或者部分远程的安排，那就更好了。不管是哪种情况，我都会保证工作时间内的投入和协作响应，不会让通勤影响交付。」
场景 C：距离确实超出承受范围 体面而诚实
适用：单程两小时以上且无法搬家，硬撑必然会离职。
核心话术：「我坦诚说一下，按现在的住址单程要两小时以上，长期每天这样跑，我担心会影响工作状态和交付质量，这对公司也是不负责任的。所以我更想先了解两个信息：一是岗位是否有部分远程或者弹性办公的空间；二是如果必须坐班，公司是否有一些通勤支持政策。如果这两点都不具备，那我可能需要重新评估自己的安排——但我想先说清楚，这不是我意愿不足，而是我希望能找到一种双方都稳定的方式。」
场景 D：面试官在试探你的薪资期望 / 是否好拿捏 守住边界
适用：对方反复追问「那你是不是可以接受低一点」这类引导。
核心话术：「通勤成本我会自己承担和规划，这不会影响我对岗位的判断。薪资这块我还是希望基于岗位职责和市场水平来沟通，我也相信公司会有合理的方案。」——不要因为「远」而主动降价，也不要因噎废食地硬顶。

5.3 完整话术示范、禁忌清单与可以反问 HR 的问题

Oral Response Script（推荐版本） 「谢谢您问到这一点，我确实算过距离，也提前想过这个问题。」

我现在住的地方到这边，单程大概一小时十分钟，比之前的通勤多一些。我的考虑是这样的：

第一，这个距离在我可接受的范围内，而且我已经在看公司附近的房子，计划入职前后完成搬迁，把通勤压缩到半小时以内。

第二，即使短期还没搬完，我也会做好时间规划，提前出门错峰通勤，保证工作时间和团队协作不受影响。

第三，我更想说说为什么愿意跑这么远来面试。 我看重的是咱们这边做的大模型应用方向跟我的经验很匹配，团队做的事情是我真正想投入的。相比省下半小时通勤，我更在意一个能长期积累的岗位。

所以结论是：通勤是我自己要解决的问题，不会成为影响工作稳定性的因素。 如果公司上下班时间有一定弹性，或者有班车之类的支持，那对我来说就更方便了——想顺便了解一下这方面的安排。
⚠️ 禁忌清单（这几句话千万不要说）：
  • ❌「先干着看看，不合适再说」 —— 直接暴露离职风险，面试官会立刻给你打上「不稳定」标签。
  • ❌「确实太远了，你们能给补贴吗」 —— 上来就谈条件，显得功利且被动，应该先给方案再了解政策。
  • ❌「我住得很近，二十分钟就到」 —— 一旦入职后被发现虚报，信任成本远高于通勤本身。
  • ❌ 抱怨前公司 / 抱怨交通 / 抱怨城市 —— 任何负面情绪外溢都会被解读为抗压能力弱。
  • ❌「只要有班车或者远程我就来」 —— 把入职条件变成了对赌，显得本末倒置。
  • ❌ 含糊其辞「还好吧，还行」 —— 回避问题反而让面试官更怀疑你根本没想过这事。
可以问 HR 的问题（姿态自然）

通勤与办公安排

  • 咱们这边上下班时间是固定的，还是有一定弹性区间？
  • 团队目前是全员坐班，还是有部分远程 / 混合办公的安排？
  • 公司或者园区有班车线路吗？覆盖哪些区域？
  • 附近租房的话，同事一般会选在哪些片区，通勤大概多久？
加分动作

把通勤转化为正面信号

  • 提到你已经实地跑过一遍路线（这说明你认真对待这次面试）。
  • 提到你有搬迁计划和时间表（这说明你能主动解决问题）。
  • 把「愿意跑远」和「对岗位方向的认可」绑定（说明你不是海投）。
  • 最后主动把话题收回到工作内容，问一句业务或技术问题，主导节奏。
🎯

本场面试的能力画像与复习锦囊

1. 全链路工程视野（End-to-End）

能从离线构建、在线召回到生成护栏完整讲清 RAG，并指出每一阶段的质量责任边界——离线决定能否召回、在线决定召回准不准、生成决定答得可不可信。

2. 量化与归因能力（Data-Driven）

所有效果结论都有评测集、指标名和对照实验支撑，并且能拆解出「哪个因素贡献了多少个点」，同时主动说明数据的局限性与适用边界。

3. 工程兜底意识（Robustness）

技术方案不只讲「怎么跑通」，还讲「超限了怎么办、没召回了怎么办、模型跑偏了怎么办」，处处有阈值、有降级、有埋点、有告警。

4. 沟通与稳定性（Soft Skills）

面对通勤这类稳定性试探，能够真诚承认、给出可落地方案、并锚定长期意愿，把潜在的减分项转化为「此人想清楚了」的加分项。

📌 上场前的三句自检：
  • 每个技术结论，我能不能说出一个具体的数字？（chunk 512、overlap 64、Top-50 重排到 Top-5、阈值 0.35、Recall@5 91.5%）
  • 每个方案，我能不能说出它的代价和适用边界？（重排 +100ms、语义分块成本高、长窗口贵且慢）
  • 每个提升，我能不能说清它是怎么测出来的？（200 条评测集、控变量、指标定义、人工复核）

Q1 RAG 全链路 2~3 分钟讲主干，留 5 分钟应对追问；Q2 上下文治理 1.5 分钟讲分层思路，重点铺「Token 预算校验」这个记忆点；Q3 检索策略 2 分钟，务必报出 RRF 公式与关键参数；Q4 分块对比 3 分钟，先讲方法再讲数据，最后主动补局限；Q5 通勤 1 分钟以内，尽快把话题交还给业务。
