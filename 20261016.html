2026年10月16日 面试试题深度简答与答辩策略

本解析面向 AI 应用开发 / RAG 工程师 岗位面试场景。本场是典型的「数据链路深挖 + 选型论证」型面试：前两题全部落在 RAG 的数据侧——先是切分架构的四维度选型论证，再是数据入库完整流水线；第三题考察Agent 项目的评估体系；第四题追问知识库数据来源与治理；最后一题回到 HR 侧的离职原因。

⚖️ 父子块 vs 单级切分 🔧 入库四环节流水线 📊 Agent 评估体系 🗂️ 数据来源与治理 🤝 离职原因应答
Q1

父子块架构与传统单级递归切分（带重叠）方案，在检索准确率、语义完整性、存储成本、检索耗时四个维度的优劣。

💡 面试官意图剖析：这是一道「选型论证题」，而且面试官把四个维度都点名了，说明他不想听「各有优劣、看场景」这种和稀泥的回答。高分结构是：① 先用一句话给出两个方案的本质差异（定性）；② 逐维度给出明确胜负 + 原因 + 量化；③ 给出「什么条件下该选谁」的判断标准；④ 主动承认父子块的代价。只夸父子块不提代价，反而会被认为没真正落地过——因为代价恰恰是它没被无脑采用的原因。

1.1 本质差异：差别不在「切几刀」，而在粒度是否解耦

我一般会先把这个定性抛出来，因为后面四个维度的胜负全部由它推导出来，而不是四个互相独立的经验结论。

传统单级递归切分（带重叠）

一个块同时干两件事

  • 切法：按分隔符优先级递归下切（\n\n → \n → 。 → 空格），块大小固定在 512/1024 token 左右，再叠加 overlap（如 64）保证接缝不丢语义。
  • 结构：只有一层。每个块既是向量化检索的单元，也是喂给大模型的生成单元。
  • 核心矛盾：为了生成要够长、够完整，为了检索要够短、够聚焦。一个块身兼两职，块长只能折中，两边都做不到最优。
父子块架构（Parent-Child / Small-to-Big）

两个粒度各司其职

  • 切法：结构感知切分后建立双层——子块 256~512 token，父块约 1500 token（通常一个父块 = 一个完整小节）。
  • 结构：子块只负责被检索（语义聚焦、区分度高），父块只负责被生成（上下文完整）。命中子块后通过 parent_id 回表取父块。
  • 核心优势：两个角色解耦，各自取最优值，不再互相妥协。
🎯 一句话定性（建议原样说出来）：
父子块本质上是「用额外的存储和一次回表查询，换取检索粒度与生成粒度的解耦」。它拿空间和时间换精度——理解了这个交换关系，四个维度的优劣就不用背了，是推导出来的。

1.2 四维度逐项拆解与胜负判定

维度 传统单级递归切分（带重叠） 父子块架构 胜负与本质原因
① 检索准确率 块长被生成需求绑架，普遍偏大（512~1024+）；块内混杂无关内容，相似度被稀释；overlap 区域还会与相邻块「抢分」，出现多条高度相似的重复命中 子块可压到 256~512，块内语义单一、向量区分度高；overlap 造成的重复命中可由父块聚合去重 父子块胜
实测 Recall@5 提升约 +7~12pt。但注意：提升来源是「能放心用小粒度检索」这个自由度，不是父子块本身有魔法
② 语义完整性 受块长限制，跨段、跨章节内容被硬切断；overlap 只能缓解接缝，且重叠部分会重复计入 token 预算 命中子块即返回完整父块，保留整个小节/完整流程，条件与结论不会分家 父子块胜
这是父子块最不可替代的优势。举例：售后流程「第 3 步」依赖「第 1 步的前提」，单级切分可能只召回第 3 步
③ 存储成本 一份文本 + 一份向量，无冗余映射 需存双层文本（父块总量 ≈ 原文，子块总量 ≈ 原文 ×(1+overlap 率)），再加 parent_id 映射与向量条数翻倍 传统胜
实测我们 300 万字语料，整体索引体积约为 1.4 倍（不是 2 倍，因为父块总和 ≈ 原文长度）
④ 检索耗时 一次向量检索即可直接拿到可生成文本，无额外步骤 额外两次开销：① 子块数量翻倍 → HNSW 候选对比次数增加；② 命中后一次 parent_id 回表查询 传统胜
实测增加约 20~60ms。但有反向因素：重排输入是更短的子块，Cross-Encoder 耗时与文本长度相关，父子块在重排环节反而可能略快
✅ 一句话记忆（四维度胜负一句话概括）：
父子块赢在「准」与「全」（前两维），输在「贵」与「慢」（后两维）。 前两维是质量，后两维是成本——所以它是一个典型的用成本换质量的架构升级，值不值得完全取决于「语义完整性是不是你当前的瓶颈」。

1.3 量化数据、决策标准与折中方案

先说我们的对照实验（控变量，只改切分方式）：同一份 200 条评测集、同一 embedding 模型、同一混合检索配置（Dense Top-50 + BM25 Top-50 + RRF），只把切分方案换掉：

评估项 单级递归切分 512 + overlap 64 父子块（子 256 / 父 1500） 差异
Recall@5 76.2% 84.0% +7.8pt
答案正确率 70.0% 79.0% +9.0pt
答案完整率（无遗漏条件/前提） 74% 89% +15pt（提升最大）
索引存储 1.0x 约 1.4x +40%
检索 P95 延迟 基线 +20~60ms 略慢

注意答案完整率提升最大（+15pt），这正好印证了前面第 ② 维的判断：父子块最核心的价值不是「召回更多」，而是「召回之后给模型的是完整的一块知识」，所以它主要治好的是「答得不全、漏条件」这类问题。

再看决策标准——什么条件下该选谁：

该选父子块

长文档 + 需要完整语义

  • 语料是制度手册、产品文档、技术规范、合同这类长文档，有清晰标题层级。
  • 用户高频问「完整流程是什么」「有哪些条件」——答案天然跨段落。
  • 线上 badcase 里「答不全 / 漏前提」占比高，而不是「找不到」占比高。
该选传统单级切分

短文本 + 成本敏感

  • 语料本身是短文本（FAQ、一句话工单、字段说明），单块自己就完整，父子块纯属冗余。
  • 存储或延迟极度敏感（海量低价值语料、边缘部署）。
  • 团队还没有稳定的评测集——没有度量就别上复杂架构，否则改坏了都不知道。
折中方案一 · 分类型路由

我们线上就是这么做的

  • 只对长文档启用父子块（制度手册、技术文档走双层）。
  • FAQ、短工单走单级切分，省存储也省延迟。
  • 收益拿到大部分，成本只涨在真正需要的部分。
折中方案二 · 句子窗口 / 缓存

用工程手段压成本

  • 句子窗口（Sentence-Window）：命中单句后带前后 N 句，粒度比父子块更细，但向量条数会爆炸，只适合小体量高价值语料。
  • 父块热点缓存：高频父块缓存在 Redis，把回表耗时从 DB 查询压到内存读取，能吃掉大部分那 20~60ms。
⚠️ 主动补一句局限（很加分）：
父子块的收益高度依赖父块边界切得对不对。如果父块本身跨了多个主题（比如把两个不相干的小节合成一个父块），那「语义完整」就变成了「噪声更多」，效果反而会掉。所以我们父块的划分严格跟着标题层级走，这也是为什么前面必须先做好 Markdown 结构还原——上游结构没做好，下游父子块就是白搭。

1.4 口述模板（建议 2 分钟）

Oral Response Script 「这两个方案我做过对照实验，我可以按四个维度分别说下结论，以及为什么。」

先说本质差异。 单级递归切分是一个块同时干两件事——既作为向量检索单元，又作为喂给大模型的生成单元，所以块长只能折中：为了生成要够长，为了检索要够短，两边都做不到最优。父子块则是把粒度解耦：子块 256 到 512 token 只负责被检索，父块大概 1500 token 只负责被生成，命中子块后回表取父块。所以它本质上是拿存储和一次回表换精度。

第一个维度，检索准确率，父子块赢。 因为它允许你把子块压得很小，块内语义单一、向量区分度就高。我们实测 Recall@5 从 76.2% 提到 84.0%，大概 8 个点。但我想强调这个提升的来源是「能放心用小粒度检索」这个自由度，不是父子块本身有什么魔法。

第二个维度，语义完整性，还是父子块赢，而且这是它最不可替代的地方。 单级切分受块长限制，跨段落的内容会被硬切断，overlap 只能缓解接缝。父子块命中就返回完整父块。数据上最明显：我们答案完整率提升了 15 个点，是所有指标里涨得最多的。比如售后流程问「第 3 步」，第 3 步其实依赖第 1 步的前提，单级切分很可能只召回第 3 步，模型就答偏了。

后两个维度父子块是输的。 存储上要存双层文本加 parent_id 映射，我们 300 万字语料实测索引体积是原来的 1.4 倍。耗时上多两次开销：子块数翻倍让 HNSW 候选对比变多，加上一次回表查询，实测增加 20 到 60 毫秒。不过这里有个反向因素——重排的输入是更短的子块，Cross-Encoder 的耗时和文本长度相关，所以重排环节父子块反而可能略快。

所以我的结论是：它不是一个「更好的切分算法」，而是一个「允许你用小粒度检索的架构」。 值不值得，取决于语义完整性是不是你当前的瓶颈。我们线上没有一刀切，而是分类型路由：制度手册、技术文档这类长文档走父子块，FAQ 和短工单走单级切分。另外我们还给高频父块加了 Redis 热点缓存，把回表那部分延迟吃掉了大半。

最后补一句：父子块的收益很依赖父块边界切得准不准。如果父块跨了好几个主题，语义完整就变成噪声更多，效果反而会掉。所以我们父块严格跟着标题层级走——这也是为什么上游的文档结构还原必须先做好。
Q2

文档解析、Markdown 优化、文本切分、双库入库这四个环节的流程说一下。

💡 面试官意图剖析：这题考的是「你对数据流水线有没有完整认知」。很多候选人只会讲「切分」这一环，一听就知道他只做过半条链路。正确姿势是按 ETL 思维讲：每个环节的输入、输出、核心动作、技术选型，并且强调上一环节的输出是下一环节的输入契约。面试官最想听到的一句话是「解析阶段丢的信息，后面永远补不回来」——这体现了你对数据侧话语权的理解。

2.1 四环节总览：一条不可逆的漏斗

环节 输入 核心动作 输出（下游契约）
① 文档解析 原始文件（PDF / Word / Excel / PPT / 图片 / HTML） 格式路由 → 文本层判定 → 版面分析 / OCR → 表格识别 带类型 + 页码 + 坐标的结构化 block 流
② Markdown 优化 block 流 标题层级推断 → 表格转 Markdown → 段落合并 → 降噪去重 干净 Markdown + 可回溯的溯源锚点
③ 文本切分 Markdown 结构感知切分 → 内容类型路由 → 父子块双层 → 元数据注入 带 parent_id 与元数据的块集合
④ 双库入库 块集合 批量向量化 → 向量库 upsert + 全文库 bulk → 一致性校验 向量库 + 全文索引库均可检索
🎯 定调（这句话是这题的灵魂）：
这四个环节是一条不可逆的漏斗——解析阶段丢掉的信息，后面任何环节都补不回来。所以我们团队把大约 60% 的调优精力放在 ①②，而不是花在检索算法上。因为知识没被正确解析、正确结构化，召回算法再花哨也救不回来。

2.2 环节一：文档解析（保真度决定上限）

  1. 格式路由：按扩展名 + MIME 分发到不同解析器，这是流水线的入口分发器。
  2. PDF 文本层判定：先尝试直接提取文本，若「有效字符数 / 页数」低于阈值，判定为扫描件，转 OCR 分支（我们用的是 PaddleOCR）。这一步很关键——不做判定，扫描件会解析出一堆空白。
  3. 版面分析：文本层用 Unstructured / pdfplumber 做版面分析，识别标题、正文、表格、图片区域，并保留每个 block 的坐标。
  4. 双栏处理：按 block 的 bbox 坐标重新排序，而不是按提取顺序。这是 PDF 解析最经典的坑。
  5. 表格识别：走表格专用提取（pdfplumber 的 table 能力或版面模型），保留行列结构，不然后面转 Markdown 就没依据。
⚠️ 这个环节我们踩过的坑：
  • 双栏 PDF 串行：直接按行提取会把左右两栏交叉拼成一句话，语义完全错乱。必须按坐标排序。
  • 扫描件倾斜 / 方向错误：需要先做方向检测和纠偏，否则 OCR 结果全是乱码。
  • 页眉页脚混入正文：每页都出现的字符串要按「跨页重复」特征识别并剔除，否则会污染所有块。

2.3 环节二：Markdown 优化（结构化中间表示）

为什么统一转 Markdown：它是目前最适合喂给大模型的中间表示——标题层级天然表达结构、表格能保留表意、列表能保留顺序、token 效率又高，而且后面第三环节可以直接按 # 的层级做结构感知切分。可以说这一环节就是为切分和生成做准备的。

动作一 · 标题层级还原

把视觉层级翻成 Markdown 层级

  • 依据字号、加粗、编号规则（第一章 / 1.1 / （一））推断 H1~H4。
  • 编号可跳级但要归一化，保证层级树是连续的。
  • 输出的是树，不是一个列表——因为切分阶段要用这棵树。
动作二 · 表格转 Markdown

保留表头是底线

  • 统一转成 Markdown 表格语法，表头必须保留。
  • 跨页表格要按表头特征识别并合并成一张，否则一张保修改价表会被拆成两张。
  • 大表后续按行分组时，每组都要重复表头。
动作三 · 段落合并与降噪

去掉 PDF 的硬换行

  • PDF 提取常把一句话按视觉宽度硬换行，要合并回完整段落，否则切分会在句中切断。
  • 剔除页眉页脚、页码、水印、目录页。
  • 多版本副本用 SimHash 做近重复检测，只留最新版。
动作四 · 保留溯源锚点

为引用回跳留后路

  • 把页码、坐标等原始定位信息以元数据形式随块保留。
  • 这样前端才能做到「答案引用可点击、高亮回原文」。
  • 一旦这步丢了，后面做引用溯源就只能重新解析一遍。
⚠️ 坑点：
伪标题是最常见的翻车点——正文里一句加粗的话被误判成标题，结果切分时把它当成了层级边界，把完整小节切碎了。我们的做法是标题判定要满足多个条件（字号 + 位置 + 编号），而不是只看加粗。

2.4 环节三：文本切分（结构与内容双重路由）

  1. 结构感知优先：按上一环节产出的标题树切，尽量让「一个块 = 一个完整小节」。只有当单个小节超过 512 token 时，才用递归字符分块做二次切分，保证不硬断句。
  2. 内容类型路由（很容易被忽略但很关键）：不是所有文本都按同样规则切——
    • 表格：整表保留成一个块，绝不从中间断开；大表按行分组但重复表头。
    • 代码 / 配置：按函数或配置段整体保留，不按行数硬切。
    • 流程步骤：编号步骤视为整体，缺任一步都会导致答案错误。
  3. 父子块双层：子块 256~512 token 用于检索；父块约 1500 token 用于生成；overlap 64 防接缝断裂。超短小节（< 80 token）向上合并，避免产生无信息量的碎片。
  4. 元数据注入：每个块带上标题面包屑（售后制度 > 退换货 > 七天无理由）、doc_id、parent_id、部门权限、生效时间、版本号、页码。
✅ 参数不是拍脑袋定的：
我们在 256 / 512 / 1024 三个 chunk size 和 0 / 64 / 128 三档 overlap 上做了 9 组对照实验，结论是 512 + overlap 64 的 Recall@5 最优。256 时召回更精准但上下文过碎、生成质量下降；1024 时噪声明显增多、MRR 反而下滑。overlap 加到 128 收益很小，但索引体积和重复结果比例都上去了。

2.5 环节四：双库入库（写入一致性是难点）

先说「双库」是哪两库、为什么得是两库：

库一 · 向量库

负责语义召回

  • 选型：Milvus / ADB-PG，索引 HNSW（M=16、efConstruction=200）。
  • 只索引子块的向量，负责「问法和原文表述不同也能召回」。
库二 · 全文索引库

负责字面精确匹配

  • 选型：Elasticsearch / OpenSearch，BM25 倒排索引。
  • 负责型号编码、精确数字、条款号这类向量补不了的盲区。
  • 顺带承载高亮与溯源原文展示。

入库写入流程（按顺序）：

Step 1 · 变更判定与批量向量化 幂等增量
用文档 doc_hash 比对判断是否变更，只重跑变更文档——全量重建一次要约 3 小时，增量降到 6 分钟。子块按批（如 64 条）调用 embedding 接口。
Step 2 · 双写：先向量库，后全文库 顺序有讲究
顺序刻意固定为「先写向量库、后写 ES」。因为如果反了，会短暂出现「ES 能搜到但向量库没有」的状态；而按我们的顺序，最坏情况是「向量有、ES 没有」——检索命中后仍能取到内容，只是关键词路少了一条，属于可降级的失败。任一步失败即进重试队列并告警。
Step 3 · 原子切换与版本标记 alias 切换
全量重建时写到新的 collection / index，完成后用 alias 原子切换，线上检索完全无感。过期文档不物理删，打 is_valid=false + 生效时间，检索时统一加时间过滤，保证历史问答可追溯。
Step 4 · 对账校验 定时巡检
定时比对两边 doc_id 集合差异，发现不一致就补写。双写最大的风险就是部分失败导致静默缺数据——表面上系统正常，实际某些文档永远搜不到，所以必须有对账。
⚠️ 这个环节的坑：
  • 换 embedding 模型要全量重建：维度或向量空间变了，旧向量不能复用，必须整库重跑——所以要提前规划，别频繁换。
  • 两库文本不一致：一边改了另一边没跟上，会导致召回高亮错位、引用对不上原文。
  • 批量 embedding 要控并发：一次塞太多会触发服务端限流（429），要配令牌桶。

2.6 口述模板（建议 2~2.5 分钟）

Oral Response Script 「这四个环节我习惯把它当成一条 ETL 流水线来讲，而且它是一条不可逆的漏斗。」

第一环，文档解析。 输入是各种原始文件，先做格式路由，然后关键一步是 PDF 文本层判定——先试着提取文本，如果每页有效字符数太低就判定为扫描件，转 OCR 分支。文本层走版面分析，保留每个 block 的坐标，按坐标重排解决双栏串行问题。输出是带类型、页码、坐标的 block 流。

第二环，Markdown 优化。 为什么要转 Markdown？因为它是最适合大模型的中间表示——标题层级天然表达结构，表格能保表意，而且后面能直接按标题切分。这一环做四件事：按字号和编号还原标题层级、表格转 Markdown 并合并跨页表格、合并 PDF 硬换行并剔除页眉页脚、以及保留页码坐标这类溯源锚点。

第三环，文本切分。 结构感知优先，尽量一个块等于一个完整小节；超长的再用递归切分兜底。然后是内容类型路由——表格整表成块、代码按函数保留、流程步骤当整体，这点很容易被忽略，但表格被切碎是事故级的错误。最后建父子块双层，子块 256 到 512 用于检索，父块 1500 用于生成，并把标题面包屑和权限、生效时间这些元数据注进去。参数是做了 9 组对照实验定的，512 加 overlap 64 最优。

第四环，双库入库。 双库是向量库加全文索引库——向量负责语义召回，ES 的 BM25 负责型号、数字、条款号这种精确匹配，单靠任何一边都覆盖不全。写入顺序我们刻意固定成先向量后 ES，因为这样最坏情况是「向量有、ES 没有」，检索命中后仍能取到内容，属于可降级的失败；反过来就会出现搜得到但取不到内容。重建时用 alias 原子切换，线上无感。增量靠 doc_hash 比对，全量 3 小时，增量 6 分钟。

最后我想强调一点： 这四个环节里前两环最容易被低估，但解析阶段丢掉的信息后面永远补不回来。所以我们把大部分调优精力放在解析和结构还原上，而不是检索算法。
Q3

你怎么评估一个 Agent 项目的好坏？

💡 面试官意图剖析：这是道开放题，考的是「你有没有评估体系」，而不是单点指标。低分回答只有一个「看准确率」。高分回答会先指出Agent 和普通问答的本质区别——Agent 是「多步决策 + 工具调用」的循环，所以过程和结果必须分开评，然后给出分层指标体系、评估方法、以及最终落到业务价值上。面试官尤其想听到「为什么不能只看最终答案」这个洞察。

3.1 先定性：Agent 评估为什么要单独一套体系

普通问答是单轮的：输入问题 → 输出答案，评估就是比对输出对不对。 而 Agent 是一个 Thought → Action → Observation 的多步循环：它会思考、选工具、填参数、看结果、再决定下一步。这意味着中间每一步都可能出错，而且错误会累积。

🎯 核心认知（这句话是本题的分水岭）：
评估 Agent 不能只看最终答案对不对，因为会漏掉两类关键情况：①「过程全错但碰巧答对」——比如绕了十个弯、调了错工具，最后蒙对了。这种不可复现，掩盖了隐患；②「过程正确但结果输在最后一跳」——比如工具调用全对、信息都拿齐了，最后格式化输出出错。这种其实方案本身可用，修一下就行。所以要把评估分成结果、过程、系统三个层次。
层次一 · 结果

任务有没有达成

端到端看目标是否完成。这是最终衡量，但不能单独使用。

层次二 · 过程

路有没有走对（Agent 专属）

看工具选择、参数填充、步数效率、错误恢复。这层是 Agent 区别于普通问答的地方。

层次三 · 系统

工程上可不可靠

稳定性、延迟、成本、安全性、可观测性——决定它能不能上线，而不只是能不能跑通。

3.2 分层指标体系（含 Agent 专属指标）

层次 指标 含义 怎么测
结果层 任务成功率 端到端是否真正达成用户目标（最重要指标） 任务评测集自动断言 + 人工复核

幻觉率 / 可溯源率 结论是否有依据、引用能否回跳原文 校验引用编号是否命中真实片段

✅ 如果只允许我报三个指标（面试时这么收尾很有力）：
任务成功率（能不能用）、工具选择 + 参数准确率（为什么能用）、单任务成本与 P95 延迟（用得起吗）。这三个覆盖了可用性、可靠性和经济性，也是业务方最关心的。

3.3 评估方法与工程落地

方法一 · 离线任务评测集 基础盘
构建任务集，必须包含多步任务和边界场景：工具失败、参数缺失、需要反问澄清、需要多工具协作。只放简单单步任务，评测出来的分数没有意义。
方法二 · 双轨评估：结果 + 轨迹 Agent 特有
这是我认为 Agent 评估里最关键的一条：不只看结果对不对，还要看轨迹合不合理。同一份轨迹数据，既断言最终状态，也检查「用了哪些工具、调了几次、有没有绕路」。这样才能定位到底是能力问题还是流程问题。
方法三 · LLM-as-a-Judge + 人工校准 成本与质量平衡
用模型做批量打分，成本低、可覆盖全量；但必须和人工金标准对齐，定期校准评分器本身，否则会出现「分数很漂亮但线上很差」。
方法四 · 对抗与鲁棒性测试 找短板
主动注入故障：工具超时、返回格式异常、权限不足、提示注入。重点看它失败时的行为——是优雅降级并告知用户，还是静默出错、甚至编造结果。
方法五 · 线上监控与回归 持续保障
线上盯 人工介入率（human-in-the-loop 接管比例，这是 Agent 最有价值的线上指标）、任务中断率、badcase 归因。任何 Prompt 或工具改动都跑一遍回归集，防回退。

3.4 口述模板与业务价值

Oral Response Script 「我会先把 Agent 和普通问答区分开，因为它们的评估逻辑不一样。」

普通问答是单轮的，评估就是看输出对不对。但 Agent 是 Thought-Action-Observation 的多步循环，它要选工具、填参数、看结果、再决定下一步，中间每一步都可能出错。所以只看最终答案是不够的，会漏掉两类情况：一种是过程全错但碰巧蒙对，这种不可复现、掩盖了隐患；另一种是过程全对、只输在最后一跳，这种其实方案能用。

所以我会分三层来评。结果层看任务成功率和正确率，这是最终衡量。过程层是 Agent 专属的，看工具选择准确率、参数正确率、轨迹效率、无效循环率、以及报错后能不能自我恢复——其中我觉得参数正确率特别重要，因为「格式合法但值填错」这种错误最隐蔽。系统层看稳定性、延迟、成本、安全性和可观测性，这层决定它能不能真上线。

如果只让我报三个指标，我会报任务成功率、工具选择加参数准确率、以及单任务成本和 P95 延迟。前两个说的是「能不能用、为什么能用」，第三个说的是「用得起吗」。

方法上，我们会建带边界场景的离线任务集，然后做双轨评估——既断言结果，也评估轨迹，用 LLM-as-a-Judge 做批量初筛再拿人工校准，另外专门做对抗测试，重点看它失败时的表现：是优雅降级并告诉用户，还是静默出错甚至编造。线上我们最看重人工介入率，它是 Agent 有没有真正取代人力的直接信号。

最后我会把它拉回业务：一个「好」的 Agent，是在可接受的成本和延迟内，用可解释的轨迹稳定完成任务，并且失败时能优雅降级而不是静默出错。 如果它跑得再准但每单成本高于人工，那在商业上也不能算好。
Q4

你们知识入库的这些数据，来源是哪里呢？

💡 面试官意图剖析：这是对项目的追问细节题，考的是数据治理意识。答不好会暴露「我的知识库只是几个测试 PDF」。要按「来源分类 → 接入方式 → 治理机制」三层回答，并主动提到权限、版本时效、更新频率、质量控制、来源可溯——这五点才是企业级知识库真正难的地方。如果只答「文档上传」，面试官立刻就知道你没做过真实项目。

4.1 数据来源全景分类

类别 典型内容 数据特点 更新频率
内部业务文档 产品手册、售后 SOP、规章制度、合同、技术文档 非结构化为主（PDF / Word），有明确版本与生效时间 周 ~ 月
结构化业务系统 CRM、ERP、OA、工单系统、订单系统 结构化、天然带部门与权限字段，可增量拉取 实时 ~ T+1
历史会话与工单 客服会话记录、工单处理方案、已解决的问答案例 天然是「问题 → 已验证答案」的问答对，价值极高 实时
内部知识门户 Confluence、内部 Wiki、知识库站点 HTML 为主，本身已有层级结构 天
外部公开资料 行业标准、法规政策、厂商官方文档 公开可获取，但时效敏感（法规会更新） 月 ~ 季
运营人工录入 badcase 补录、新政策临时通知 量小但质量最高、针对性强 按需
✅ 这题最值得主动说出来的一句话：
历史工单是最被低估的数据源。 它天然就是「用户真实问法 → 人工验证过的答案」的问答对，可以直接用来构建评测集和做 few-shot 示例。我们 200 条的 Golden Dataset 有一大半就是从历史会话里抽出来再人工标注的。这么说一句，面试官立刻知道你懂数据闭环。

4.2 接入方式与增量同步

方式一 · 批量文件接入

适合文档类

  • 运营后台上传、目录挂载扫描、对象存储（OSS/S3）批量拉取。
  • 适合产品手册、制度文档这类成批更新的资料。
方式二 · API 定时拉取

适合业务系统

  • 定时任务调业务系统接口，按 updated_at 拉增量。
  • CRM / 工单系统这类持续变化的数据走这条路。
方式三 · 数据库直连

适合结构化数据

  • 只读账号直连从库，按时间戳或自增 ID 增量抽取。
  • 把行数据拼成自然语言段落再入库，否则检索效果很差。
  • 必须只读，避免影响业务库。
方式四 · 爬虫与人工回灌

补齐最后两块

  • 爬虫：抓取内部 Wiki（需鉴权），按页面结构解析。
  • 人工回灌：线上 badcase 由运营补录标准答案后重新入库，形成闭环。

每条数据都必须携带的元数据（这是下游权限和时效控制的基础）： doc_id、source_url（或原始路径）、dept（归属部门）、effective_date / expire_date、version、doc_hash。

4.3 权限、版本与质量治理（企业级真正的难点）

治理一 · 权限隔离 不是效果问题，是安全问题
部门可见性作为元数据写入每个块，检索时做 pre-filter 前置过滤。注意不能在检索后再筛——否则会出现「Top-5 里 4 条都是越权文档，过滤后只剩 1 条」的召回崩塌。这条既影响效果，更是合规底线。
治理二 · 版本与时效 旧版必须失效
过期文档不物理删除，打 is_valid=false 并保留生效/失效时间，检索统一加时间过滤。这样既能保证「问旧政策问到的是当时的版本」，也保留了历史问答的可追溯性。
治理三 · 去重与多版本收敛 SimHash
同一份制度往往存在多个副本和多个版本。用 SimHash 做近重复检测，只保留最新版，旧版归档。不做这一步，回答里会同时出现新旧两个标准，模型极容易答错。
治理四 · 更新频率与增量 T+1 + 变更触发
常规走每日 T+1 定时增量；对时效敏感的数据（如临时通知）支持变更触发即时入库。用 doc_hash 判断是否真的变了，避免无效重建。
治理五 · 质量闭环与溯源 数据飞轮
线上采集无召回埋点、点踩率，每周做 badcase 归因并分类：是「知识库没有 → 补数据」还是「有但没召回 → 修检索/切分」。同时每个块都能回溯到原文档和页码，支撑引用高亮与人工核对。这样数据质量才能持续提升，而不是一次性导入就烂在那里。

4.4 口述模板（建议 1.5 分钟）

Oral Response Script 「我们的数据来源主要有五类，我按类别说下，然后重点讲下接入和治理。」

第一类是内部业务文档，产品手册、售后 SOP、规章制度、技术文档这些，以 PDF 和 Word 为主，大概 1.2 万份。特点是有版本、有生效时间。第二类是结构化业务系统，CRM、工单、订单这些，走数据库只读直连或者 API 增量拉取，它们天然带部门权限字段。第三类是历史会话和工单——这块我觉得最被低估，因为它天然就是「用户真实问法加人工验证过的答案」的问答对，我们评测集一大半是从这里抽的。第四类是内部 Wiki，走爬虫抓。第五类是运营人工录入，主要是线上 badcase 补录，量不大但质量最高。

接入方式上，文档类走批量上传和对象存储扫描，业务系统走定时 API 或数据库增量，每条数据都必须带 doc_id、来源、归属部门、生效时间和版本号——这些元数据是下游权限控制和时效过滤的基础。

但我觉得真正难的不是接入，是治理，我讲四点。第一是权限：部门可见性要做成检索前置过滤，不能检索完再筛，否则 Top-5 里可能四条都是越权文档，过滤完之后召回就崩了，这既是效果问题也是合规底线。第二是版本时效：过期文档不删，打标记加时间过滤，保证问到旧政策时给的是当时的版本。第三是去重：同一份制度经常有好几个副本和版本，我们用 SimHash 做近重复检测，只留最新版，不然回答里会同时冒出新旧两个标准。第四是质量闭环：线上采集无召回埋点和点踩，每周做 badcase 归因，区分是「知识库没有」还是「有但没召回」——前者补数据，后者修检索，这样数据质量才会持续变好，而不是导进去就烂在那里。
Q5

你上一份工作为什么离开？

💡 面试官意图剖析：这是一道「情商 + 稳定性」双重考察题。面试官想听三件事：① 你为什么走（原因是否合理、客观）；② 你怎么讲（有没有抱怨前雇主，暴露情绪管理问题）；③ 你会不会也这样离开我们（稳定性预判）。核心原则只有一条：可以讲事实，不要带情绪；聚焦「我要去哪里」，而不是「我受够了什么」。抱怨前公司是这道题最大的减分项，没有之一。

5.1 应答三原则与回答结构

原则一 · 客观归因，不指责

讲外部化、可验证的原因

优先讲业务调整、项目方向变化、个人发展瓶颈这类客观原因。避免「领导不行」「同事甩锅」「公司管理混乱」——这些话会让面试官想：你到我们这儿会不会也这么说。

原则二 · 聚焦成长，指向新机会

结尾必须落回这里

讲完原因后一定要接一句「所以我来到贵司，因为这里能做 XX」。把「离开的原因」自然转化为「选择你们的理由」。

原则三 · 真诚且有边界

不编造、不过度自曝

不要编离谱理由（大厂规模一查便知）。也不要过度展开前公司的内部矛盾——讲得越细，越像在抱怨。一句客观陈述 + 一句成长诉求，足够。

回答结构（四步）

事实 → 原因 → 反思 → 指向

① 客观陈述发生了什么；② 说明这与我的职业规划哪里不匹配；③ 这段经历让我更清楚自己要什么；④ 所以我现在特别看重贵司的 XX。

5.2 五种场景应答模板（挑最贴近你真实情况的）

场景 A：项目 / 业务方向调整 ⭐ 最稳妥
适用：项目收缩、业务线合并、方向被砍，你被迫换方向。
话术：「我上一份工作主要在做 XX 方向，后来公司做了战略调整，这个项目被收缩、团队并入了其他组，日常重心转到了 XX。我更希望继续在 AI 应用这个方向深入做下去，所以选择看外部机会。这段经历也让我更确定，我想找一个能长期投入的技术方向。」
场景 B：成长遇到瓶颈 主动进取型
适用：技术栈停滞、长期做维护和重复需求。
话术：「在上一家我已经把负责的模块做到相对稳定，进入日常维护阶段，更多是需求交付，很难再接触到更复杂的系统设计。我希望能在一个业务复杂度更高、能持续提升自己的平台。所以我在看机会的时候，特别关注岗位的技术深度和业务场景。」
场景 C：公司经营问题 / 裁员 客观诚实型
适用：融资受挫、业务收缩、团队整体优化。
话术：「公司去年因为业务收缩做了一轮人员调整，我们团队整体被优化。我不太想把这件事说得多么委屈，客观就是公司战略变了。这段经历让我在选择时更看重两点：一是业务本身的健康度，二是岗位的长期匹配度，而不只是短期薪资。」
场景 D：客观原因（通勤 / 家庭 / 异地） 点到为止
适用：真实原因是距离或家庭安排。
话术：「主要是客观的通勤原因，上一家公司单程要将近两小时，长期下来对状态和交付都有影响。这个问题我已经想好了解决方案——如果有合适的平台，我会搬到公司附近。所以这不会成为我这次选择的障碍。」
注意：点到为止，不要展开家庭细节。可以参考本页 Q5 通勤题的完整话术。
场景 E：试用期未过 / 短期离职 最难，需谨慎
适用：入职时间很短就离开，简历上看得出来，无法回避。
话术：「我坦诚说，那段时间我发现实际工作内容和面试沟通的差异比较大，我主要负责的是 XX，跟我的方向不太匹配。我不想长期待在一个自己贡献有限的位置上，所以比较早做了调整。这件事也让我学会在入职前把职责边界和团队方向问得更清楚——所以今天我也想问一下，这个岗位前三个月最核心的目标是什么。」
关键：把「及时止损」讲成成熟的判断，并顺势转到反向提问，掌握主动权。切勿说「大家都在混」「学不到东西」。

5.3 完整话术示范、禁忌清单与追问应对

Oral Response Script（推荐版本） 「主要原因是项目方向调整，我想继续在 AI 应用这个方向深耕。」

我上一份工作主要负责 XX 方向的开发，其中一部分就是 AI 应用相关的落地。后来公司做了战略调整，这条业务线被收缩，团队并入了其他组，日常重心转到了比较传统的 XX 业务上。

这不是谁的问题，是公司整体方向变了。 我理解公司的选择，但对我来说，我希望能在 AI 应用这个方向上持续积累，而不是频繁切换赛道。所以经过考虑，我决定出来看看更匹配的机会。

这段经历也让我更清楚自己要什么。 我现在选机会最看重两点：一是业务本身在做的事情有没有长期价值，二是这个岗位能不能让我在这个方向上做深。这也是我今天来这里面试的原因——贵司这边做的 XX 和我的经验很匹配，是我真正想投入的方向。

所以我的离开是一个基于职业规划的正常选择， 不存在和团队或者公司的不愉快。我也希望下一份工作能做长做深。
⚠️ 禁忌清单（这几句千万别说）：
  • ❌ 骂前领导 / 前同事 —— 最致命的减分项，直接暴露情绪管理和团队协作风险。
  • ❌「加班太多受不了」 —— 会被直接解读为抗压能力不足，哪怕事实如此。
  • ❌「公司太乱、没有流程」 —— 显得你只会挑刺，不能适应真实环境。
  • ❌「就是想休息一段时间」 —— 暗示你随时可能再休息，稳定性直接归零。
  • ❌ 详细吐槽技术栈落后 / 项目没技术含量 —— 显得不专业，也贬低了团队。
  • ❌ 编造可被验证为假的原因 —— 背景调查或简单追问就会穿帮，信任彻底崩塌。
  • ❌「钱太少」作为唯一理由 —— 可以说，但要包装成「岗位价值与回报不匹配」，且最好不是唯一原因。
追问一

「那你以后会不会也这样离开我们？」

「正因为上次的原因，我这次选得特别慎重。我在了解岗位时会特别确认业务方向、团队规划和我能负责的范围，这些确认清楚了，我是希望长期做下去的。这也是我为什么对这个岗位问得比较细的原因。」

追问二

「上一家薪资多少？为什么涨得不多？」

「上一家的薪资在我这个层级属于正常水平。不过我这次更看重的是平台和方向，薪资希望基于岗位职责和市场水平来谈，我也相信贵司会有合理的方案。」——不要因为着急就自降身价。

追问三（最好的情况）

「那你希望我们这边是什么样的？」

这是送分题，说明对方在认真评估匹配度。答「我最希望的是能在一个方向持续做深，有明确的业务目标，团队里有人能互相 review」——把诉求说得专业且可满足。

主动把话题收回到业务

回答完立刻反问一个业务或技术问题，比如「咱们这个方向目前最大的技术挑战是什么」，把节奏从「审问」拉回「交流」。参考本页 Q5 通勤题的同类技巧。

本场面试的能力画像与复习锦囊

1. 架构选型的论证能力（Trade-off）

面对父子块 vs 单级切分这种二选一，能用一句话定性本质差异（粒度是否解耦），再逐维度推导出胜负，并主动承认代价与适用边界——而不是背四条结论。

2. 数据链路的完整视野（Data Pipeline）

能把解析 → 优化 → 切分 → 双库入库讲成一条有输入输出契约的 ETL 流水线，知道「解析阶段丢的信息后面补不回来」，并且说得出每环节的具体坑。

3. 评估体系而非单点指标（Evaluation System）

Agent 评估能分结果层、过程层、系统层，知道参数正确率和人工介入率这类「隐蔽但关键」的指标，并把评估最终落到业务 ROI 上。

4. 数据治理意识（Governance）

知识库来源不止是「上传文档」，还包含业务系统、历史工单、Wiki 和人工回灌；并且能说出权限前置过滤、版本时效、去重、质量闭环这四个真正的难点。

📌 上场前的三句自检：
  • 每个技术结论，我能不能说出一个具体的数字？（子块 256~512 / 父块 1500 / overlap 64 / 索引 1.4 倍 / 延迟 +20~60ms / Recall@5 76.2%→84.0% / 完整率 +15pt）
  • 每个方案，我能不能说出它的代价和适用边界？（父子块 +40% 存储、回表延迟、父块边界依赖上游结构；双库双写一致性风险）
  • 每个结论，我能不能说清它是怎么测出来的？（200 条评测集、9 组参数对照、控变量、LLM-as-Judge + 人工校准）

Q1 切分选型 2 分钟，先定性再逐维度，务必说出「父子块是用存储换解耦」这句总结；Q2 四环节 2~2.5 分钟，按 ETL 顺序讲，重点铺「不可逆漏斗」和「先向量后 ES」两个记忆点；Q3 Agent 评估 2 分钟，先讲为什么不能只看结果，再给三层指标，收尾报三个核心指标；Q4 数据来源 1.5 分钟，五类来源快速过，把时间留给治理四点；Q5 离职原因 1 分钟以内，客观陈述后立刻把话题转到岗位匹配度上。
